\begin{abstract}
Large configurable systems such as the Linux kernel, BusyBox, coreboot, Barebox, and Das U-Boot describe what gets compiled with Kbuild-style Makefiles: a per-directory \texttt{obj-\$(CONFIG\_X)}-shaped vocabulary layered on GNU Make, driven by a Kconfig-defined space of Boolean and tristate options. A single build under one \texttt{.config} answers only which files were selected for \emph{that} configuration; it does not explain how the build varies across the astronomical configuration space, which is what developers need to triage crashes across unfamiliar hardware variants, bound the blast radius of configuration changes, synthesize minimal reproducing environments, or identify dead source files silently abandoned by build refactorings.

We present \textbf{skbuild}, a symbolic-execution engine for the Kbuild-relevant subset of GNU Make that computes, for every object file, a Z3-checkable Boolean condition over Kconfig symbols describing exactly when that file participates in the build. While a naive fork-per-branch execution strategy suffers catastrophic path explosion ($2^N$ paths, exhausting memory even on small fixtures), skbuild maintains a \emph{single symbolic state} per Kbuild file, representing each Make variable as a map of guarded words and merging conditional branches back into that single state eagerly with branch-guard regating and scoped overwrite preservation.

We evaluate skbuild across five major configurable codebases spanning 26.9 million lines of code: BusyBox 1.36.1, coreboot 4.22.01, Barebox 2024.01.0, Das U-Boot 2024.01, and the 1,565-Makefile Linux kernel tree (totaling 2,050 Makefiles and 18,175 extracted object targets). skbuild achieves 91.0\%--99.5\% construct coverage across 59,345 observed constructs, processes utility and firmware corpora in under 6.3\,s and the entire Linux tree in 22.1\,s (<105\,MB peak RSS), and agrees with live compiler builds across Z3-generated witness suites with up to 99.0\% agreement. Furthermore, we demonstrate seven software engineering applications enabled by exact build conditions: (1) reducing continuous integration matrices by up to 90\% via greedy set-cover while guaranteeing 98.2\%--100\% object coverage; (2) discovering real dead code and build bugs, including 6 provably unreachable firmware drivers in Barebox; (3) detecting Kconfig-Kbuild divergence (18 orphan variables in U-Boot); (4) analyzing differential build evolution across major releases via SMT equivalence ($\text{SAT}(\phi_{\text{v1}} \oplus \phi_{\text{v2}})$); (5) quantifying feature interaction degree (identifying hotspots up to $k=16$ interacting flags); (6) synthesizing minimal bug-reproducing configurations in milliseconds via Z3 MaxSAT; and (7) clustering co-compiled components into exact equivalence classes.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Modern systems software is defined by immense configurability. Operating system kernels, bootloaders, embedded hypervisors, and core system utilities do not compile a single, monolithic binary from a static list of source files. Instead, systems such as the Linux kernel, Das U-Boot, Barebox, coreboot, and BusyBox rely on \textbf{Kbuild}---a domain-specific convention built on top of GNU Make and driven by the \textbf{Kconfig} configuration language~\cite{berger2010variability,dietrich2012variability,kmax,tartler2011dead}. In Kbuild, per-directory Makefiles declare target object files conditionally using configuration variables (e.g., \texttt{obj-\$(CONFIG\_USB) += usb.o}), construct composite targets from multiple sub-objects, nest assignments inside complex conditional blocks (\texttt{ifeq}, \texttt{ifdef}), and recursively traverse subdirectories whose inclusion is itself gated by configuration flags.

Each configuration variable (\texttt{CONFIG\_*}) is governed by a declarative Kconfig specification defining its type: Boolean (\texttt{y} vs.\ unset/\texttt{n}), tristate (\texttt{y} for built-in, \texttt{m} for loadable module, \texttt{n} for disabled), integer, or string. A single execution of \texttt{make} under a concrete \texttt{.config} file materializes only a single point in an astronomical configuration space. For example, the x86 Linux kernel alone contains over 15,000 configuration options, yielding a potential state space exceeding $2^{15000} \approx 10^{4500}$ configurations~\cite{tartler2011dead,liebig2010analysis,apel2013feature,berger2013variability}.

\subsection{Motivating Use Cases in Systems Engineering}
\label{sec:intro:use-cases}

While concrete builds answer whether a file is compiled for \emph{one specific configuration}, critical software engineering workflows require knowing the complete \textbf{presence condition} $\Phi(o)$---a Boolean formula over configuration symbols that defines exactly when object file $o$ is compiled. We highlight four practical scenarios where knowing $\Phi(o)$ is indispensable:

\paragraph{1. Production Crash-Dump Analysis \& Root-Cause Triage.}
When an embedded device, mobile phone, or cloud node crashes in production, the crash report typically records a stack trace identifying a specific C source file, function name, and offset. However, the exact \texttt{.config} of the deployment environment may be lost, proprietary, modified by an OEM, or stripped of debug metadata. Knowing $\Phi(o)$ allows developers to determine immediately which configuration settings could have enabled the faulty subsystem, dramatically pruning the hypothesis space during root-cause analysis. For example, in Android kernel maintenance across hundreds of device variants (Qualcomm, MediaTek, Samsung Exynos), pinpointing whether a crash in a memory controller driver could have occurred on a specific carrier model requires verifying whether that driver's presence condition is satisfiable under that model's base configuration.

\paragraph{2. Pre-Commit Static Analysis \& Patch Verification.}
Automated code review bots and static analyzers (e.g., Clang-Tidy, Coverity, Infer) require a syntactically valid translation unit with appropriate compiler macros and header paths to analyze a patch~\cite{melo2016variability,liebig2011variability}. When a pull request touches a source file, the analyzer must synthesize a valid build configuration that actually compiles that file. Without $\Phi(o)$, analyzers either guess default configurations (often failing to compile optional drivers) or perform expensive brute-force search. With $\Phi(o)$, an SMT solver generates a satisfying assignment in milliseconds, guaranteeing that the target translation unit is activated.

\paragraph{3. Continuous Integration (CI) Matrix Optimization.}
Configurable software projects struggle with severe CI budget limits. Testing all configurations is mathematically impossible, while testing only \texttt{defconfig} leaves 70\%--90\% of the codebase uncompiled~\cite{medeiros2016comparison,ishimwe2021dynaplex}. By computing $\Phi(o)$ for all targets, CI systems can formulate a \emph{Set-Cover} optimization problem to synthesize the smallest possible test matrix that guarantees 100\% source code coverage.

\paragraph{4. Build System Maintenance, Dead Code, \& Refactoring.}
As build systems evolve over decades, dead target rules accumulate~\cite{tartler2011dead,passos2013coevolution,nadi2014where}. If an object file's presence condition is provably unsatisfiable ($\Phi(o) \equiv \text{False}$), the code is dead and can never be built under any configuration. Conversely, maintainers refactoring Makefiles need to prove that their changes preserve build equivalence ($\text{UNSAT}(\Phi_{\text{old}}(o) \oplus \Phi_{\text{new}}(o))$).

\subsection{Challenges of Symbolic Kbuild Analysis}
\label{sec:intro:challenges}

Extracting exact presence conditions from Kbuild Makefiles requires symbolic execution of GNU Make semantics. However, GNU Make presents subtle language semantics that distinguish it sharply from traditional programming languages and build systems like CMake~\cite{cybolic}:

\begin{itemize}
\item \textbf{Variable Flavor Semantics (Simple vs.\ Recursive Expansion):} GNU Make variables possess distinct expansion flavors. \emph{Simply expanded} variables (\texttt{:=}, \texttt{::=}) expand references immediately upon assignment, freezing their value. In contrast, \emph{recursively expanded} variables (\texttt{=}, \texttt{?=}) store unexpanded text and perform expansion dynamically at every point of lookup. Furthermore, the appending operator (\texttt{+=}) inherits the flavor of the existing variable, behaving as simple concatenation if previously simple, or recursive deferred expansion if previously recursive.
\item \textbf{Conditionally-Named Overwrites and Guarded Scoping:} A common Kbuild idiom involves assigning to variable names constructed dynamically from configuration options, such as \texttt{obj-\$(CONFIG\_A) := 1.o}. When \texttt{CONFIG\_A=y}, this statement acts as an overwrite on the variable \texttt{obj-y}. However, under configurations where \texttt{CONFIG\_A!=y}, this assignment does not target \texttt{obj-y}. A naive symbolic executor that blindly replaces \texttt{obj-y} with \texttt{1.o} would clobber contributions made by prior statements under other configurations. The analyzer must track \emph{guarded overwrites}, ensuring prior values survive under the negation of the assignment condition.
\item \textbf{Recursive Directory Traversal with Conditional Inheritance:} Kbuild distributes build logic across hundreds of per-directory Makefiles. A parent Makefile includes subdirectories conditionally via target variables (e.g., \texttt{obj-\$(CONFIG\_DRIVERS) += drivers/}). A target $o$ declared in a subdirectory is compiled only if both the directory itself is reached by the parent \emph{and} the local condition within the subdirectory evaluates to true: $\Phi(o) = \Phi_{\text{dir}} \wedge \phi_{\text{local}}(o)$.
\item \textbf{Multi-Stage Target Vocabularies:} Modern firmware and embedded bootloaders divide compilation into distinct execution stages. For example, coreboot defines \texttt{bootblock-y}, \texttt{romstage-y}, \texttt{ramstage-y}, and \texttt{smm-y}; Barebox defines \texttt{pbl-y} (pre-bootloader); and U-Boot defines \texttt{spl-y} (secondary program loader) and \texttt{tpl-y} (tertiary program loader). Symbolic execution must parameterize and track these heterogeneous target families simultaneously.
\end{itemize}

\subsection{The Path Explosion Problem and Eager Merge}
\label{sec:intro:path-explosion}

A classical symbolic executor (such as KLEE~\cite{cadar2008klee} or DART~\cite{godefroid2005dart}) explores programs by \textbf{forking} execution state at each conditional branch. When applied to Kbuild, a fork-per-branch strategy splits the symbolic state into two separate paths at every \texttt{ifeq}, \texttt{ifneq}, \texttt{ifdef}, and \texttt{ifndef} directive.

In practice, Kbuild Makefiles contain dense sequences of conditional statements. Because Make does not provide native scoping or structured block closures for most variables, statements interact globally across the file. After $N$ sequential branch points, a fork-per-branch executor maintains $O(2^N)$ live states. In our experiments (\Cref{sec:eval:rq0}), a synthetic 7-statement Makefile already produces 32 active paths, and analyzing BusyBox's top-level Makefiles exhausts available system memory after generating over 10,000 forked paths.

To overcome this fundamental limitation, skbuild adopts and adapts the \textbf{Single-State Eager-Merge} architecture pioneered by Cybolic~\cite{cybolic}. Instead of maintaining multiple paths, skbuild maintains exactly \emph{one} symbolic state per Kbuild file. Each variable's value is represented as a set of \emph{guarded words} $\langle \text{word}, \phi \rangle$, where $\phi$ is the Z3 Boolean formula under which $\text{word}$ is present in the variable. When encountering a conditional block, skbuild clones the state, executes both branches independently, and \emph{immediately merges} the resulting states back into a single unified state. Contributions from the then-branch are conjoined with the branch guard $\psi$, while contributions from the else-branch are conjoined with $\neg \psi$. This maintains an execution complexity of $O(N \cdot B)$ (where $B$ is the small branch factor), eliminating path explosion entirely.

\subsection{Contributions}
\label{sec:intro:contributions}

In this paper, we make the following contributions:

\begin{enumerate}
\item \textbf{Eager-Merge Symbolic Execution for Kbuild:} We formalize the semantics of GNU Make and Kbuild under single-state eager merge, defining sound operational rules for simple vs.\ recursive variable expansion, guarded overwrite preservation, branch-guard regating, macro expansion, and recursive directory traversal (\Cref{sec:semantics}, \Cref{sec:traversal}).
\item \textbf{Pure-Python, SMT-Backed Implementation:} We present \textbf{skbuild}, an open-source tool implementing this architecture with Mozilla \texttt{pymake}-based AST parsing and an incremental Z3 SMT solving layer (\Cref{sec:impl}).
\item \textbf{Comprehensive Empirical Evaluation on 5 Major Systems:} We evaluate skbuild across five widely used production systems: the Linux Kernel, Das U-Boot, Barebox, coreboot, and BusyBox---totaling 26.9 million lines of code, 2,050 Makefiles, and 18,175 target objects (\Cref{sec:eval}).
\item \textbf{Exhaustive Construct Census:} We report a construct-coverage census classifying 59,345 observed syntactic constructs, demonstrating 91.0\%--99.5\% modeled coverage and over 99.9\% effective coverage (\Cref{sec:eval:rq2}).
\item \textbf{Real Build Validation:} We validate extracted presence conditions against live compiler builds on four platforms (BusyBox, coreboot QEMU x86, Barebox sandbox, U-Boot sandbox) using Z3-generated greedy set-cover witness configurations, achieving 94.7\%--99.4\% precision and identifying zero symbolic logic errors (\Cref{sec:eval:rq4}).
\item \textbf{Seven Software Engineering Applications:} We demonstrate practical applications enabled by skbuild: CI matrix reduction, real build bug and dead code discovery (including 6 dead PMU firmware targets in Barebox), Kconfig-Kbuild divergence linting (18 orphan variables in U-Boot), differential build evolution across major releases, feature interaction hotspot analysis ($k=16$), minimal reproducing configuration synthesis via Z3 MaxSAT, and co-compilation architectural clustering (\Cref{sec:eval:apps}).
\end{enumerate}

\section{Overview \& Motivating Example}
\label{sec:overview}

To illustrate the mechanics of Kbuild symbolic execution and the difference between fork-per-branch and eager-merge strategies, consider the realistic Kbuild snippet shown in \Cref{lst:example}.

\begin{lstlisting}[language=make,caption={A motivating Kbuild example exhibiting conditional selection, guarded overwrites, and flavor expansion.},label={lst:example}]
# 1. Conditional append
obj-$(CONFIG_NET) += net_core.o

# 2. Guarded overwrite (target variable name is conditional)
obj-$(CONFIG_OPTIMIZED) := fast_net.o

# 3. Dynamic appending
obj-$(CONFIG_OPTIMIZED) += net_accel.o
obj-$(CONFIG_SECURITY)  += firewall.o

# 4. Conditional branching with recursive re-assignment
ifeq ($(CONFIG_ARCH_64),y)
  TARGET_WIDTH := 64
else
  TARGET_WIDTH := 32
endif

# 5. Expanding target with computed variable
obj-y += driver_$(TARGET_WIDTH).o
\end{lstlisting}

\subsection{Trace of Execution under Eager Merge}
\label{sec:overview:trace}

Let us trace how skbuild's single-state representation evolves across these statements:

\begin{itemize}
\item \textbf{Line 1 (\texttt{obj-\$(CONFIG\_NET) += net\_core.o}):} The expression \texttt{\$(CONFIG\_NET)} expands symbolically to value \texttt{y} under condition $\texttt{CONFIG\_NET}=\texttt{y}$. Thus, \texttt{obj-y} receives \texttt{net\_core.o} with guard $\phi_1 = (\texttt{CONFIG\_NET}=\texttt{y})$.
\item \textbf{Line 2 (\texttt{obj-\$(CONFIG\_OPTIMIZED) := fast\_net.o}):} This statement uses simple overwrite \texttt{:=}. When $\texttt{CONFIG\_OPT}=\texttt{y}$, it assigns to \texttt{obj-y}. However, it must preserve the previous value of \texttt{obj-y} when $\texttt{CONFIG\_OPT}\neq\texttt{y}$:
\begin{align*}
\phi(\mathtt{fast\_net.o}) &= (\texttt{CONFIG\_OPT}=\texttt{y}) \\
\phi(\mathtt{net\_core.o}) &= \phi_1 \wedge \neg(\texttt{CONFIG\_OPT}=\texttt{y}) \\
&= (\texttt{CONFIG\_NET}=\texttt{y}) \wedge (\texttt{CONFIG\_OPT}\neq\texttt{y})
\end{align*}
\item \textbf{Line 3 (\texttt{obj-\$(CONFIG\_OPTIMIZED) += net\_accel.o}):} Appending adds \texttt{net\_accel.o} under $(\texttt{CONFIG\_OPT}=\texttt{y})$ and \texttt{firewall.o} under $(\texttt{CONFIG\_SEC}=\texttt{y})$.
\item \textbf{Line 4 (Conditional Block \texttt{ifeq}):} skbuild evaluates branch condition $\psi = (\texttt{CONFIG\_64}=\texttt{y})$.
  \begin{itemize}
  \item In the \emph{then}-branch, a cloned state assigns $\mathtt{TARGET\_WIDTH} \gets \langle \mathtt{64}, \text{True} \rangle$.
  \item In the \emph{else}-branch, a cloned state assigns $\mathtt{TARGET\_WIDTH} \gets \langle \mathtt{32}, \text{True} \rangle$.
  \item At \texttt{endif}, skbuild merges the two branches:
  $$\{ \langle \mathtt{64}, \texttt{CONFIG\_64}=\texttt{y} \rangle, \; \langle \mathtt{32}, \texttt{CONFIG\_64}\neq\texttt{y} \rangle \}$$
  \end{itemize}
\item \textbf{Line 5 (\texttt{obj-y += driver\_\$(TARGET\_WIDTH).o}):} Expanding $\mathtt{TARGET\_WIDTH}$ yields:
  \begin{align*}
  \mathtt{driver\_64.o} &\text{ with guard } (\texttt{CONFIG\_64}=\texttt{y}) \\
  \mathtt{driver\_32.o} &\text{ with guard } (\texttt{CONFIG\_64}\neq\texttt{y})
  \end{align*}
\end{itemize}

\subsection{Fork-per-Branch State Explosion vs.\ Eager Merge}
\label{sec:overview:fork-vs-merge}

To contrast the fundamental scaling behavior of traditional fork-per-branch execution against skbuild's eager merge, consider the structural difference in how execution states propagate.

In a fork-per-branch model, when execution reaches a conditional directive with branch condition $\psi$, the entire memory image (variable bindings, target lists, expansion flags) is duplicated. Path 1 continues with constraint $\Gamma \wedge \psi$, and Path 2 continues with $\Gamma \wedge \neg \psi$. If a Makefile contains a sequence of $N$ conditional directives:
\begin{align*}
\mathtt{ifeq\ (\$(CONFIG\_A),y)}\ & \dots\ \mathtt{endif} \\
\mathtt{ifeq\ (\$(CONFIG\_B),y)}\ & \dots\ \mathtt{endif} \\
&\;\;\vdots \\
\mathtt{ifeq\ (\$(CONFIG\_N),y)}\ & \dots\ \mathtt{endif}
\end{align*}
the number of active leaf execution states grows as $2^N$. Even if each branch modifies only a single local variable, every state maintains its own independent copy of the entire variable namespace. At $N=20$, the executor must track $1{,}048{,}576$ states. When encountering loops or helper macro expansions, state growth becomes catastrophic, resulting in memory exhaustion (OOM).

In contrast, skbuild's single-state eager merge collapses the branches immediately at the \texttt{endif}. At the statement level, the number of active states remains strictly $1$. The conditional variation is pushed down into the word conditions $\mathcal{M}(w)$ of the specific variables modified inside the branch. Variables that were not modified inside the branch are completely untouched. Consequently, skbuild's memory footprint scales linearly with the number of unique variable assignments ($O(V \cdot |\mathcal{M}|)$), independent of the branch depth $N$.

\subsection{Composite Objects and Helper Variables}
\label{sec:overview:composite}

In large Kbuild systems, object files are frequently declared as \emph{composite objects} formed by linking multiple sub-objects into a single binary. For example, in the Linux networking subsystem:
\begin{lstlisting}[language=make]
obj-$(CONFIG_IPV6) += ipv6.o
ipv6-objs := ip6_output.o ip6_input.o addrconf.o
ipv6-$(CONFIG_INET6_AH) += ah6.o
ipv6-$(CONFIG_INET6_ESP) += esp6.o
\end{lstlisting}
Here, \texttt{ipv6.o} is a composite target whose component sub-objects are defined in the helper variable \texttt{ipv6-objs} and dynamically appended via \texttt{ipv6-\$(CONFIG\_INET6\_AH)}. 

When extracting presence conditions, skbuild resolves composite dependencies by expanding the component lists under the composite target's condition. If $\Phi(\mathtt{ipv6.o}) = (\texttt{CONFIG\_IPV6} = \mathtt{"y"})$ and $\phi_{\text{sub}}(\mathtt{ah6.o}) = (\texttt{CONFIG\_INET6\_AH} = \mathtt{"y"})$, the presence condition for sub-object \texttt{ah6.o} is:
\begin{align*}
\Phi(\mathtt{ah6.o}) &= \Phi(\mathtt{ipv6.o}) \wedge \phi_{\text{sub}}(\mathtt{ah6.o}) \\
&= (\texttt{CONFIG\_IPV6} = \mathtt{"y"}) \wedge (\texttt{CONFIG\_INET6\_AH} = \mathtt{"y"})
\end{align*}
skbuild automatically resolves composite mappings across standard Kbuild prefix conventions (\texttt{target-objs}, \texttt{target-y}, and \texttt{target-m}).

\subsection{Why Kbuild Is Not a Generic Symbolic-Execution Target}
\label{sec:overview:why-different}

A reasonable question is why Kbuild requires a purpose-built symbolic executor rather than treating it as a generic imperative program. Four domain-specific properties of GNU Make and Kbuild motivate skbuild's architecture:

\begin{enumerate}
\item \textbf{Dynamic LHS Variable Names:} In standard programming languages, the target variable of an assignment is a static identifier. In Kbuild, the variable name itself is computed dynamically (e.g., \texttt{obj-\$(CONFIG\_FOO)}). The identity of the mutated variable depends on symbolic inputs, requiring symbolic resolution of target identifiers before assignment.
\item \textbf{Dual Flavor Expansion Semantics:} Unlike languages with uniform eager or lazy evaluation, GNU Make mixes eager simple assignment (\texttt{:=}) and deferred recursive assignment (\texttt{=}) within the same file. Variables carry their flavor dynamically, governing whether future \texttt{+=} appends expand immediately or defer.
\item \textbf{Directory-Level Conditional Inheritance:} Kbuild distributes build specifications across recursive directory trees. Variable values do not propagate via function returns; instead, presence conditions accumulate hierarchically through directory-entry target variables.
\item \textbf{Tristate and String Configuration Algebras:} Kconfig symbols operate over a 4-element domain $\{ \mathtt{"y"}, \mathtt{"m"}, \mathtt{"n"}, \mathtt{undef} \}$. Symbolic reasoning requires exact encoding of tristate semantics, where \texttt{obj-\$(CONFIG\_X)} encompasses both built-in (\texttt{y}) and modular (\texttt{m}) targets.
\end{enumerate}

\section{Symbolically Executing Kbuild Makefiles}
\label{sec:semantics}

In this section, we formalize the abstract syntax, state representation, and execution rules of skbuild.

\subsection{Syntax and Language Subset}
\label{sec:semantics:syntax}

Kbuild Makefiles are parsed into an Abstract Syntax Tree (AST) representing statements $s \in \mathcal{S}$:
\begin{align*}
s \;::=\; &\mathtt{SetVar}(x, \odot, e) &&\text{assignment: } \odot \in \{ \mathtt{:=}, \mathtt{::=}, \mathtt{=}, \mathtt{?=} , \mathtt{+=} \} \\
\mid\; &\mathtt{If}(\psi, s_{\text{then}}, s_{\text{else}}) &&\text{conditional block (\texttt{ifeq}, \texttt{ifneq}, \texttt{ifdef}, \texttt{ifndef})} \\
\mid\; &\mathtt{Include}(e) &&\text{inclusion of auxiliary Makefile or fragments} \\
\mid\; &\mathtt{Rule}(targets, prereqs, cmds) &&\text{build rule (classified out-of-scope for presence conditions)}
\end{align*}
Expressions $e$ consist of literal strings, variable expansions \texttt{\$(VAR)}, and built-in function calls \texttt{\$(func arg1, arg2)}.

\subsection{Guarded Variable Representation}
\label{sec:semantics:varg}

Every Make variable $x$ in skbuild is modeled as a \textbf{Guarded Variable} $\text{VarG}(x)$, defined as:
$$\text{VarG}(x) = \langle \mathcal{M}, \mathcal{F} \rangle$$
where:
\begin{itemize}
\item $\mathcal{M}: \mathcal{W} \to \mathcal{B}_{\text{Z3}}$ is a finite map from words $w \in \mathcal{W}$ to Z3 Boolean formulas $\phi \in \mathcal{B}_{\text{Z3}}$ representing the condition under which $w$ belongs to $x$.
\item $\mathcal{F} \in \{ \text{Simply}, \text{Recurse} \}$ represents the expansion flavor of $x$.
\end{itemize}

A \textbf{Symbolic State} $\sigma \in \Sigma$ is a mapping from variable names to their guarded representations:
$$\sigma: \text{VarName} \to \text{VarG}$$
Throughout symbolic execution, skbuild maintains a single global state $\sigma$ per directory.

\subsection{Guarded Algebraic Operations}
\label{sec:semantics:algebra}

We define three fundamental algebraic operations over guarded word maps $\mathcal{M}_1, \mathcal{M}_2: \mathcal{W} \to \mathcal{B}_{\text{Z3}}$:

\begin{enumerate}
\item \textbf{Guarded Map Disjunction ($\mathcal{M}_1 \sqcup \mathcal{M}_2$):}
$$(\mathcal{M}_1 \sqcup \mathcal{M}_2)(w) = \begin{cases}
\mathcal{M}_1(w) \vee \mathcal{M}_2(w) & \text{if } w \in \text{dom}(\mathcal{M}_1) \cap \text{dom}(\mathcal{M}_2) \\
\mathcal{M}_1(w) & \text{if } w \in \text{dom}(\mathcal{M}_1) \setminus \text{dom}(\mathcal{M}_2) \\
\mathcal{M}_2(w) & \text{if } w \in \text{dom}(\mathcal{M}_2) \setminus \text{dom}(\mathcal{M}_1)
\end{cases}$$

\item \textbf{Condition-Gated Scaling ($\psi \odot \mathcal{M}$):}
$$(\psi \odot \mathcal{M})(w) = \psi \wedge \mathcal{M}(w) \quad \text{for all } w \in \text{dom}(\mathcal{M})$$

\item \textbf{Guarded Overwrite Preservation ($\mathcal{M}_{\text{old}} \setminus_{\psi} \mathcal{M}_{\text{new}}$):}
When an overwrite occurs under condition $\psi$, existing words in $\mathcal{M}_{\text{old}}$ survive under $\neg \psi$:
$$(\mathcal{M}_{\text{old}} \setminus_{\psi} \mathcal{M}_{\text{new}})(w) = (\psi \odot \mathcal{M}_{\text{new}})(w) \sqcup (\neg\psi \odot \mathcal{M}_{\text{old}})(w)$$
\end{enumerate}

\subsection{Structural Operational Semantics}
\label{sec:semantics:sos}

We formalize the execution of Kbuild statements using big-step operational semantics. A configuration is a tuple $\langle s, \sigma, \Gamma \rangle$, where $s$ is the statement to execute, $\sigma$ is the current symbolic state, and $\Gamma$ is the accumulated path condition. The transition relation $\langle s, \sigma, \Gamma \rangle \Downarrow \sigma'$ specifies that executing $s$ under state $\sigma$ and path guard $\Gamma$ yields updated state $\sigma'$.

\Cref{fig:sos-rules} presents the deductive inference rules governing skbuild.

\subsection{Branch Execution and Eager State Merging}
\label{sec:semantics:merge}

When encountering a conditional block $\mathtt{If}(\psi, s_{\text{then}}, s_{\text{else}})$:

\begin{enumerate}
\item skbuild queries Z3 to test whether the \emph{then}-branch is satisfiable under the current path guard: $\text{SAT}(\Gamma \wedge \psi)$. If satisfiable, it clones state $\sigma_{\text{then}} \gets \text{clone}(\sigma)$ and executes $s_{\text{then}}$ under path guard $\Gamma \wedge \psi$.
\item Similarly, it checks $\text{SAT}(\Gamma \wedge \neg \psi)$. If satisfiable, it clones $\sigma_{\text{else}} \gets \text{clone}(\sigma)$ and executes $s_{\text{else}}$ under path guard $\Gamma \wedge \neg \psi$.
\item \textbf{Eager Merge:} skbuild computes the set of variables modified in either branch: $\mathcal{V}_{\text{touched}} = \text{touched}(\sigma_{\text{then}}) \cup \text{touched}(\sigma_{\text{else}})$.
For each variable $x \in \mathcal{V}_{\text{touched}}$, the merged map $\mathcal{M}_{\text{merged}}$ is formed by regating the branch contributions:
$$\mathcal{M}_{\text{merged}}(w) = \left( \psi \wedge \mathcal{M}_{\text{then}}(w) \right) \vee \left( \neg \psi \wedge \mathcal{M}_{\text{else}}(w) \right)$$
Any variable not modified in a branch retains its pre-branch state conjoined with that branch's guard.
\end{enumerate}

\begin{algorithm}[t]
\caption{Single-State Eager-Merge Symbolic Execution}
\label{alg:eager-merge}
\begin{algorithmic}[1]
\Function{ExecStatement}{$\sigma, \Gamma, s$}
  \If{$s$ is $\mathtt{SetVar}(x_{\text{exp}}, \odot, e)$}
    \State $\mathit{names} \gets \mathrm{ExpandNames}(x_{\text{exp}}, \sigma)$
    \State $\mathit{vals} \gets \mathrm{ExpandVals}(e, \sigma, \odot)$
    \For{$(x, \phi_x) \in \mathit{names}$}
      \For{$(w, \phi_w) \in \mathit{vals}$}
        \State $\psi \gets \Gamma \wedge \phi_x \wedge \phi_w$
        \If{$\mathrm{IsSat}(\psi)$}
          \State $\sigma.\mathrm{SetVar}(x, \odot, w, \psi)$
        \EndIf
      \EndFor
    \EndFor
  \ElsIf{$s$ is $\mathtt{If}(\psi_{\text{cond}}, s_{\text{then}}, s_{\text{else}})$}
    \State $\sigma_{\text{then}} \gets \text{null}; \; \sigma_{\text{else}} \gets \text{null}$
    \If{$\mathrm{IsSat}(\Gamma \wedge \psi_{\text{cond}})$}
      \State $\sigma_{\text{then}} \gets \mathrm{ExecBlock}(\mathrm{Clone}(\sigma), \Gamma \wedge \psi_{\text{cond}}, s_{\text{then}})$
    \EndIf
    \If{$\mathrm{IsSat}(\Gamma \wedge \neg \psi_{\text{cond}})$}
      \State $\sigma_{\text{else}} \gets \mathrm{ExecBlock}(\mathrm{Clone}(\sigma), \Gamma \wedge \neg \psi_{\text{cond}}, s_{\text{else}})$
    \EndIf
    \State $\sigma \gets \mathrm{MergeStates}(\sigma, \Gamma, \psi_{\text{cond}}, \sigma_{\text{then}}, \sigma_{\text{else}})$
  \ElsIf{$s$ is $\mathtt{Include}(path_{\text{exp}})$}
    \State $\mathit{paths} \gets \mathrm{ExpandVals}(path_{\text{exp}}, \sigma, \mathtt{:=})$
    \For{$(p, \phi_p) \in \mathit{paths}$}
      \State $\mathrm{ExecFile}(\sigma, \Gamma \wedge \phi_p, p)$
    \EndFor
  \EndIf
  \State \Return $\sigma$
\EndFunction
\end{algorithmic}
\end{algorithm}

\Cref{alg:eager-merge} summarizes the execution loop. Because every branch is merged immediately, the number of active states remains exactly 1 at all statement boundaries.

\subsection{Built-in Functions and Macro Expansions}
\label{sec:semantics:builtins}

GNU Make code in Kbuild relies on built-in text manipulation functions. skbuild models these functions symbolically over guarded word maps:
\begin{itemize}
\item $\mathtt{\$(filter\ } pattern, text \mathtt{)}$: Evaluates pattern matching over guarded words, retaining only matching elements with their associated conditions:
$$\text{filter}(p, \mathcal{M}) = \{ \langle w, \phi \rangle \in \mathcal{M} \mid \text{match}(p, w) \}$$
\item $\mathtt{\$(filter\text{-}out\ } pattern, text \mathtt{)}$: Retains words that do not match the pattern:
$$\text{filter-out}(p, \mathcal{M}) = \{ \langle w, \phi \rangle \in \mathcal{M} \mid \neg\text{match}(p, w) \}$$
\item $\mathtt{\$(patsubst\ } pattern, replacement, text \mathtt{)}$: Applies pattern substitution to each guarded word, preserving its guard $\phi$:
$$\text{patsubst}(p, r, \mathcal{M}) = \{ \langle \text{subst}(p, r, w), \phi \rangle \mid \langle w, \phi \rangle \in \mathcal{M} \}$$
\item $\mathtt{\$(subst\ } from, to, text \mathtt{)}$: Replaces substring occurrences in all words.
\item $\mathtt{\$(addprefix\ } prefix, text \mathtt{)}$ and $\mathtt{\$(addsuffix\ } suffix, text \mathtt{)}$: Prepends/appends literals to each guarded word:
$$\text{addprefix}(pfx, \mathcal{M}) = \{ \langle pfx \cdot w, \phi \rangle \mid \langle w, \phi \rangle \in \mathcal{M} \}$$
\item $\mathtt{\$(call\ } macro, arg1, \ldots \mathtt{)}$: Binds positional arguments \texttt{\$(1)}, \texttt{\$(2)} in a local scope and evaluates the macro body under eager merge.
\item Arithmetic macros: Evaluates \texttt{\$(int-add a, b)}, \texttt{\$(int-subtract a, b)}, \texttt{\$(int-multiply a, b)}, and \texttt{\$(bool-to-mask bool)} directly.
\end{itemize}

\section{Recursive Traversal \& Build Condition Extraction}
\label{sec:traversal}

Having defined intra-file symbolic execution, we now describe how skbuild traverses multi-directory project trees and extracts final presence conditions.

\subsection{Subdirectory Discovery and Recursive Exploration}
\label{sec:traversal:subdirs}

In Kbuild, directory recursion is declared through target variables containing directory paths (e.g., \texttt{obj-y += drivers/}, \texttt{obj-\$(CONFIG\_FS) += fs/}). During symbolic execution of a Makefile $M$ at path $P$, skbuild identifies all words $w \in \mathcal{M}(x)$ for target variables $x$ (such as \texttt{obj-y}, \texttt{obj-m}, \texttt{lib-y}, \texttt{core-y}) that correspond to directory paths.

Let $\phi_{\text{sub}}$ be the condition associated with directory path $D$ in Makefile $M$. If $M$ was reached under directory condition $\Phi_M$, then subdirectory $D$ is entered under the inherited directory presence condition:
$$\Phi_D = \Phi_M \wedge \phi_{\text{sub}}$$
skbuild schedules directory $D$ for analysis with initial path condition $\Phi_D$. If a directory is referenced multiple times under different conditions $\phi_1, \phi_2$, its incoming presence condition is the disjunction $\Phi_D = \Phi_M \wedge (\phi_1 \vee \phi_2)$. To prevent infinite loops caused by cyclic inclusions or directory symlinks, skbuild tracks visited paths and updates presence conditions incrementally.

\subsection{Multi-Stage Target Extraction}
\label{sec:traversal:stages}

Different configurable systems organize compilation into distinct target variables. skbuild uses configurable target prefixes:
\begin{itemize}
\item \textbf{Linux Kernel \& BusyBox:} \texttt{obj-}, \texttt{lib-}, \texttt{core-}, \texttt{drivers-}, \texttt{net-}, \texttt{libs-}, \texttt{head-}.
\item \textbf{coreboot:} \texttt{bootblock-}, \texttt{verstage-}, \texttt{romstage-}, \texttt{postcar-}, \texttt{ramstage-}, \texttt{smm-}, \texttt{subdirs-}.
\item \textbf{Barebox:} \texttt{obj-}, \texttt{pbl-}, \texttt{lwip-}, \texttt{driver-}, \texttt{common-}.
\item \textbf{Das U-Boot:} \texttt{obj-}, \texttt{lib-}, \texttt{spl-}, \texttt{tpl-}, \texttt{vpl-}.
\end{itemize}

When analysis completes across all directories, skbuild collects all target object files $o$ (words ending in \texttt{.o} or \texttt{.a}). For each object file $o$ in directory $D$ with local condition $\phi_{\text{local}}(o)$, the global presence condition is:
$$\Phi(o) = \Phi_D \wedge \phi_{\text{local}}(o)$$

\begin{algorithm}[t]
\caption{Recursive Hierarchy Traversal and Build Condition Extraction}
\label{alg:recursive-traversal}
\begin{algorithmic}[1]
\Function{ExtractBuildConditions}{$\mathit{rootDir}, \mathit{settings}$}
  \State $\mathit{workQueue} \gets [(\mathit{rootDir}, \text{True})]$
  \State $\mathit{visitedDirs} \gets \emptyset; \; \mathit{targetConditions} \gets \text{Map}()$
  \While{$\mathit{workQueue} \neq \emptyset$}
    \State $(D, \Phi_D) \gets \mathrm{PopFront}(\mathit{workQueue})$
    \If{$D \in \mathit{visitedDirs}$}
      \State $\mathrm{UpdateDirCond}(\mathit{targetConditions}, D, \Phi_D)$
      \State \textbf{continue}
    \EndIf
    \State $\mathit{visitedDirs} \gets \mathit{visitedDirs} \cup \{ D \}$
    \State $\sigma_D \gets \mathrm{AnalyzeDirectory}(D, \mathit{settings})$
    \For{$(o, \phi_{\text{local}}) \in \sigma_D.\mathrm{GetTargetObjects}()$}
      \State $\Phi(o) \gets \Phi_D \wedge \phi_{\text{local}}$
      \State $\mathit{targetConditions}[o] \gets \mathit{targetConditions}[o] \vee \Phi(o)$
    \EndFor
    \For{$(D_{\text{sub}}, \phi_{\text{sub}}) \in \sigma_D.\mathrm{GetSubdirectories}()$}
      \State $\mathrm{PushBack}(\mathit{workQueue}, (D_{\text{sub}}, \Phi_D \wedge \phi_{\text{sub}}))$
    \EndFor
  \EndWhile
  \State \Return $\mathit{targetConditions}$
\EndFunction
\end{algorithmic}
\end{algorithm}

\Cref{alg:recursive-traversal} details the full recursive extraction algorithm.

\subsection{SMT Encoding of Boolean and Tristate Domains}
\label{sec:traversal:smt}

Kbuild symbols are translated into Z3 expressions over their configuration domains:
\begin{itemize}
\item \textbf{Boolean Variables (\texttt{bool}):} Modeled as equality with string literal \texttt{"y"}: $\texttt{CONFIG\_X} = \mathtt{"y"}$. Unset is represented as $\texttt{CONFIG\_X} = \mathtt{undef}$ or $\neg(\texttt{CONFIG\_X} = \mathtt{"y"})$.
\item \textbf{Tristate Variables (\texttt{tristate}):} Modeled over domain $\{ \mathtt{"y"}, \mathtt{"m"}, \mathtt{"n"}, \mathtt{undef} \}$. An object in \texttt{obj-y} has condition $\texttt{CONFIG\_X} = \mathtt{"y"}$; an object in \texttt{obj-m} has condition $\texttt{CONFIG\_X} = \mathtt{"m"}$; and composite targets \texttt{obj-\$(CONFIG\_X)} include both built-in and modular builds: $(\texttt{CONFIG\_X} = \mathtt{"y"}) \vee (\texttt{CONFIG\_X} = \mathtt{"m"})$.
\end{itemize}
All presence conditions are simplified via Z3's tactic pipeline (\texttt{ctx-simplify}, \texttt{propagate-values}, \texttt{elim-uncnstr}).

\subsection{SMT-Based Minimal Test Matrix \& Delta Debugging}
\label{sec:traversal:maxsat}

Given the full mapping of extracted presence conditions $\mathcal{T} = \{ (o_1, \Phi_1), \ldots, (o_n, \Phi_n) \}$, skbuild synthesizes minimal configuration test suites and isolating configurations using SMT solving:

\begin{algorithm}[t]
\caption{SMT-Based Minimal Test Suite Synthesis via Greedy Set-Cover}
\label{alg:set-cover}
\begin{algorithmic}[1]
\Function{SynthesizeCIMatrix}{$\mathcal{T}$}
  \State $\mathit{uncovered} \gets \{ o \mid (o, \Phi) \in \mathcal{T} \text{ and } \mathrm{IsSat}(\Phi) \}$
  \State $\mathit{testConfigs} \gets []$
  \While{$\mathit{uncovered} \neq \emptyset$}
    \State $\mathit{target} \gets \mathrm{SelectNextTarget}(\mathit{uncovered})$
    \State $\mathit{model} \gets \mathrm{GetSatisfyingModel}(\Phi_{\mathit{target}})$
    \State $\mathit{config} \gets \mathrm{ModelToConfig}(\mathit{model})$
    \State $\mathit{coveredByConfig} \gets \emptyset$
    \For{$o \in \mathit{uncovered}$}
      \If{$\mathrm{EvalUnderConfig}(\Phi_o, \mathit{config}) == \text{True}$}
        \State $\mathit{coveredByConfig} \gets \mathit{coveredByConfig} \cup \{ o \}$
      \EndIf
    \EndFor
    \State $\mathit{uncovered} \gets \mathit{uncovered} \setminus \mathit{coveredByConfig}$
    \State $\mathit{testConfigs}.\mathrm{Append}((\mathit{config}, \mathit{coveredByConfig}))$
  \EndWhile
  \State \Return $\mathit{testConfigs}$
\EndFunction
\end{algorithmic}
\end{algorithm}

\Cref{alg:set-cover} iteratively synthesizes concrete witness configurations that maximize the marginal coverage of previously uncompiled target objects until 100\% of satisfiable targets are covered. Furthermore, to synthesize the \emph{minimal reproducing configuration} for a specific bug-triggering target $o^*$, skbuild invokes Z3 \texttt{Optimize} (MaxSAT), asserting $\Phi(o^*)$ as a hard constraint and $\neg \texttt{CONFIG\_X}$ for all other symbols as soft constraints, producing the minimal set of enabled flags in milliseconds.

\subsection{Differential Build Equivalence Analysis}
\label{sec:traversal:diff}

To analyze how build systems evolve across versions or refactorings, skbuild computes differential build equivalence between two versions $\mathcal{T}_1$ and $\mathcal{T}_2$:

\begin{algorithm}[t]
\caption{Differential Build Equivalence and Change Impact Analysis}
\label{alg:diff-analysis}
\begin{algorithmic}[1]
\Function{AnalyzeDifferentialEvolution}{$\mathcal{T}_1, \mathcal{T}_2$}
  \State $\mathit{added} \gets \mathrm{dom}(\mathcal{T}_2) \setminus \mathrm{dom}(\mathcal{T}_1)$
  \State $\mathit{removed} \gets \mathrm{dom}(\mathcal{T}_1) \setminus \mathrm{dom}(\mathcal{T}_2)$
  \State $\mathit{common} \gets \mathrm{dom}(\mathcal{T}_1) \cap \mathrm{dom}(\mathcal{T}_2)$
  \State $\mathit{identical} \gets \emptyset; \; \mathit{widened} \gets \emptyset; \; \mathit{restricted} \gets \emptyset; \; \mathit{diverged} \gets \emptyset$
  \For{$o \in \mathit{common}$}
    \State $\Phi_1 \gets \mathcal{T}_1[o]; \; \Phi_2 \gets \mathcal{T}_2[o]$
    \If{$\neg \mathrm{IsSat}(\Phi_1 \oplus \Phi_2)$}
      \State $\mathit{identical} \gets \mathit{identical} \cup \{ o \}$
    \ElsIf{$\neg \mathrm{IsSat}(\Phi_1 \wedge \neg \Phi_2)$}
      \State $\mathit{widened} \gets \mathit{widened} \cup \{ o \}$
    \ElsIf{$\neg \mathrm{IsSat}(\Phi_2 \wedge \neg \Phi_1)$}
      \State $\mathit{restricted} \gets \mathit{restricted} \cup \{ o \}$
    \Else
      \State $\mathit{witness} \gets \mathrm{GetSatisfyingModel}(\Phi_1 \oplus \Phi_2)$
      \State $\mathit{diverged} \gets \mathit{diverged} \cup \{ (o, \mathit{witness}) \}$
    \EndIf
  \EndFor
  \State \Return $(\mathit{added}, \mathit{removed}, \mathit{identical}, \mathit{widened}, \mathit{restricted}, \mathit{diverged})$
\EndFunction
\end{algorithmic}
\end{algorithm}

\Cref{alg:diff-analysis} partitions common targets into provably identical, generalized ($\Phi_1 \implies \Phi_2$), restricted ($\Phi_2 \implies \Phi_1$), or diverged targets, automatically providing concrete witness configurations demonstrating the divergence.

\section{Implementation}
\label{sec:impl}

skbuild is implemented in pure Python 3 (approximately 2,500 lines of core engine code) with bindings to the Z3 SMT solver (\texttt{z3-solver} 4.12+). The architecture consists of four modular components:
\begin{enumerate}
\item \textbf{AST Parser (\texttt{pymake3}):} A modernized Python 3 port of Mozilla's \texttt{pymake} GNU Make parser, enhanced with support for Kconfig macro expansions, order-only prerequisites (\texttt{|}), and shell probe interceptors.
\item \textbf{Symbolic State Engine (\texttt{ds.py}, \texttt{symexe.py}):} Implements $\text{VarG}$, single-state eager merge, branch regating, and guarded overwrite resolution.
\item \textbf{Macro \& Function Expander (\texttt{expansion.py}):} Evaluates built-in Make functions (\texttt{filter}, \texttt{filter-out}, \texttt{subst}, \texttt{patsubst}, \texttt{addprefix}, \texttt{addsuffix}, \texttt{call}, \texttt{foreach}) symbolically over guarded word vectors.
\item \textbf{SMT Constraint Solver (\texttt{zsolver.py}):} Encapsulates Z3 incremental solver instances, tactic simplification, memoized satisfiability checking, and witness model extraction.
\end{enumerate}

\section{Discussion \& Threats to Validity}
\label{sec:threats}

\subsection{Threats to Validity}
\label{sec:threats:validity}

\emph{Internal Validity.} Threats to internal validity concern potential defects in skbuild's symbolic execution engine or Z3 formula encodings. We mitigated this through extensive regression test suites (\texttt{make test}, \texttt{make busybox-check}) and end-to-end real build validations across four independent systems (\Cref{sec:eval:rq4}), verifying zero symbolic logic errors.

\emph{External Validity.} Threats to external validity concern whether our findings generalize to other Kbuild systems. We evaluated five distinct codebases spanning operating systems (Linux), system utilities (BusyBox), and firmware/bootloaders (coreboot, Barebox, U-Boot) across 26.9M LOC and 2,050 Makefiles.

\emph{Construct Validity.} skbuild extracts presence conditions under the assumption that Makefile target variables govern file compilation. Discrepancies in sandbox environments arise primarily from architecture-independent host utility harnesses linking files outside Kbuild rules.

\subsection{Limitations}
\label{sec:threats:limitations}

\emph{Unmodeled Shell Side Effects.} skbuild evaluates host and compiler probe \texttt{\$(shell ...)} invocations conservatively while ignoring recipe command lines. Our construct census confirms that dynamic scripts modifying target variables are absent in standard Kbuild rules.

\emph{Kbuild Satisfiability vs.\ Kconfig Cross-Tree Validity.} skbuild computes Make-satisfiable presence conditions $\Phi(o)$. While $\Phi(o)$ is satisfiable in isolation, Kconfig cross-tree constraints (\texttt{select}, \texttt{depends on}) may prevent certain variable assignments from co-occurring in a valid \texttt{.config}. Integrating a full Kconfig parser to compute $\Phi_{\text{Kbuild}} \wedge \Phi_{\text{Kconfig}}$ represents a natural direction for future work.

\section{Related Work}
\label{sec:related}

\subsection{Variability-Aware Analysis \& Software Product Lines}
Analyzing highly configurable software has received extensive attention in software engineering~\cite{berger2010variability,berger2013variability,dietrich2012variability,erwig2011choice,liebig2010analysis,tartler2011dead,ishimwe2021dynaplex,nadi2014where,passos2013coevolution,medeiros2016comparison}. Tools such as TypeChef~\cite{kenner2010typechef} and SuperC~\cite{gazzillo2012superc} parse C source code with conditional preprocessor directives (\texttt{\#ifdef}), extracting presence conditions over source ASTs. skbuild complements preprocessor analysis by operating at the build system level, determining which translation units enter the compiler in the first place.

\subsection{Build System Analysis \& Condition Extraction}
Dietrich et al.~\cite{dietrich2012variability} and Berger et al.~\cite{berger2010variability,berger2013variability} studied the variability models of Kconfig and the Linux kernel. kmax~\cite{kmax} parses Kbuild files using custom grammar patterns to extract constraints. skbuild differs fundamentally by executing GNU Make semantics via symbolic interpretation with exact flavor expansion, guarded overwrites, and SMT solving. Cybolic~\cite{cybolic} recently introduced eager-merge symbolic execution for CMake build systems; skbuild adapts and formalizes this architecture for Kbuild's distinct flavor semantics, recursive Make structures, and stage target vocabularies.

\subsection{Symbolic Execution in Software Engineering}
Symbolic execution~\cite{king1976symbolic,cadar2008klee,godefroid2005dart} is widely used for test generation and bug finding. While traditional symbolic executors fork paths at conditional branches, recent work on state merging and variational execution~\cite{kuznetsov2012efficient,nguyen2014using,nguyen2020kbuild} folds paths into disjunctive summaries. skbuild applies eager merging directly to the domain of configuration-driven build systems.

\section{Conclusion}
\label{sec:conclusion}

We presented \textbf{skbuild}, a symbolic-execution engine for Kbuild Makefiles that extracts exact, Z3-checkable presence conditions for compiled object files. By replacing fork-per-branch execution with single-state eager merge, skbuild avoids path explosion and scales to large production systems, analyzing the entire Linux kernel (1,565 Makefiles) in 22.1\,s (<105\,MB RAM). Evaluated across five systems spanning 26.9M LOC, skbuild achieves over 99.9\% effective construct coverage, validates against live compiler builds with up to 99.4\% precision, and enables powerful applications including CI matrix reduction, dead code discovery, Kconfig divergence linting, and release evolution analysis. skbuild is open source at \url{https://github.com/dynaroars/skbuild}.
