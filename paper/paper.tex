\title{Variability-Aware Analysis of Kbuild Makefiles}

\author{Anonymous Author(s)}

\begin{abstract}
  The Linux kernel is one of the most configurable software systems, and its \texttt{kbuild} Makefiles control how thousands of configuration options determine which source files are compiled and linked into the kernel build.
  To understand why a source file is omitted from a build, or which configuration options enable it, a developer needs its build condition: a logical formula over configuration options that specifies when the file is built.
  Invoking Make on a single configuration reveals only the files compiled for that configuration, while exhaustively enumerating all configurations is intractable.
  Standard symbolic execution spawns new execution paths at every conditional branch and suffers from path explosion, whereas prior family-based static analyses of Kbuild Makefiles enumerate complete string definitions for each variable.
  We present \tool{}, a symbolic execution approach for \texttt{kbuild} Makefiles that maintains a consolidated symbolic state mapping each Make variable to a set of guarded words, where each word is paired with a path constraint over configuration options in the style of a value summary.
  Append statements add guarded words incrementally, overwrites perform guarded updates that exclude the new path constraint from existing words, and state merging combines the symbolic states of conditional branches at join points, keeping the symbolic state proportional to the number of distinct words in each variable.
  We represent the resulting build conditions as quantifier-free first-order formulae and use an SMT solver to check their satisfiability and generate valid configurations.

\section{Motivating Example}
  \label{sec:example}
  This section walks through the symbolic execution of a Kbuild Makefile in \tool{} to illustrate how build conditions are computed and how the consolidated symbolic state remains compact.
  At a high level, the Linux kernel is built in two steps: configuring and building~\cite{nguyen2020kbuild}.
  In the configuration step, a developer selects features using a configurator that reads Kconfig files, which specify configuration options and their dependencies, and writes the chosen settings to a \texttt{.config} file.
  Boolean options take the value \texttt{y} to include a feature or remain unset to exclude it, while tristate options take \texttt{y} (built directly into the kernel), \texttt{m} (compiled as a loadable kernel module), or unset.
  In the build step, Kbuild uses GNU Make to evaluate Makefiles and determine which source files to compile and link.
  Programmers encode variability in Kbuild Makefiles by populating reserved variables known as goal definitions: \texttt{obj-y} lists object files built into the kernel image and \texttt{obj-m} lists object files built as modules.
  Makefiles support runtime variable name construction~\cite{gazzillo2017kmax}: a statement such as \texttt{obj-\$(CONFIG\_EXT4\_FS) += ext4.o} expands the configuration option on the left-hand side to form the target variable name \texttt{obj-y}, \texttt{obj-m}, or \texttt{obj-} (which Kbuild ignores).

  \autoref{lst:example} shows a Kbuild Makefile adapted from the Linux \texttt{ext4} file system.
  A developer who modifies a source file in this directory and runs a build may ask why \texttt{ext4.o} was omitted from the build, or which configuration settings would compile it.
  Running Make with a single \texttt{.config} file answers this question for one configuration at a time.
  A build condition summarizes this behavior across the configuration space as a logical constraint over configuration options that specifies when the file is included in the build.

  \begin{figure}[t]
  \begin{lstlisting}[style=kbuild]
  obj-$(CONFIG_EXT4_FS) += ext4.o
  obj-$(CONFIG_EXT4_KUNIT_TESTS) := ext4-inode-test.o
  ifeq ($(CONFIG_FS_VERITY),y)
    EXTRA := verity
  else
    EXTRA := crypto
  endif
  obj-y += $(EXTRA).o
  ext4-inode-test-y += inode-test.o
  \end{lstlisting}
  \caption{Makefile adapted from Linux \texttt{fs/ext4/Makefile}. Only line~1 is verbatim; lines~2 and~9 are adapted and lines~3--8 are constructed to add an overwrite, a conditional, and a composite object.}
  \Description{A nine-line Kbuild Makefile with an append, an overwrite, a conditional assignment, and a composite file.}
  \label{lst:example}
  \end{figure}

  Let $E_y$ and $E_m$ denote the predicates \texttt{CONFIG\_EXT4\_FS=y} and \texttt{=m}, $T_y$ and $T_m$ denote the corresponding settings of \texttt{CONFIG\_\allowbreak EXT4\_\allowbreak KUNIT\_\allowbreak TESTS}, and $V$ denote \texttt{CONFIG\_FS\_VERITY=y}.
  \tool{} treats configuration options as symbolic inputs and simulates the evaluation of the Makefile over a single consolidated state.
  Each Make variable is mapped to a variational set of words~\cite{walkingshaw2014variational} in which each word is paired with a guard over configuration options, so the membership of each word forms a Boolean value summary in the sense of MultiSE~\cite{sen2015multise}.
  Line~1 expands the left-hand side and appends \texttt{ext4.o} to \texttt{obj-y} under guard $E_y$ and to \texttt{obj-m} under guard $E_m$.
  Line~2 is a conditional overwrite whose left-hand side also depends on a tristate option: under $T_y$ it overwrites \texttt{obj-y} with \texttt{ext4-inode-test.o}, and under $T_m$ it overwrites \texttt{obj-m}.
  To preserve existing words on paths where the overwrite does not take effect, \tool{} performs a guarded update~\cite{sen2015multise,gazzillo2017kmax}: it adds \texttt{ext4-inode-test.o} to \texttt{obj-y} under $T_y$ and to \texttt{obj-m} under $T_m$, while conjoining the negated guard with the prior entries so that \texttt{ext4.o} remains in \texttt{obj-y} under $E_y \land \neg T_y$ and in \texttt{obj-m} under $E_m \land \neg T_m$.
  Lines~3--7 assign \texttt{EXTRA} in both branches of an \texttt{ifeq} conditional; at the join point, state merging combines the two branches into a single symbolic state mapping \texttt{EXTRA} to \texttt{verity} under $V$ and \texttt{crypto} under $\neg V$.
  Line~8 expands \texttt{\$(EXTRA)} and concatenates each alternative with \texttt{.o}, appending two guarded words with complementary guards to \texttt{obj-y}.
  Finally, line~9 defines \texttt{inode-test.o} as a member of the composite object \texttt{ext4-inode-test.o}, which inherits the build condition of its parent composite.
  \autoref{tab:example} lists the resulting build conditions.
  These conditions are local to \texttt{fs/ext4/Makefile}; the full build condition of each file conjoins the condition under which Kbuild descends into \texttt{fs/ext4/}.

  Representing build conditions as quantifier-free first-order formulae allows \tool{} to answer developer queries directly with a satisfiability modulo theories (SMT) solver.
  Evaluated against a concrete \texttt{.config}, the formula for \texttt{ext4.o} explains why the file was excluded from the build, \eg, because $T_y$ holds and overwrote \texttt{obj-y}.
  Conjoined with the feature-model constraints extracted from Kconfig, the formula enables an SMT solver to find a satisfying assignment that compiles \texttt{ext4.o} by satisfying $E_y \land \neg T_y$.
  \tool{} exposes these two analyses through the \texttt{why} and \texttt{config-for} commands; \autoref{sec:eval} validates the solver-generated configurations with the kernel configurator and concrete builds.

  Prior symbolic execution of Kbuild Makefiles by Nguyen and Nguyen~\cite{nguyen2020kbuild} follows conventional path-based exploration: it forks a new execution state at every conditional or multi-valued expansion and mitigates path explosion by combining execution paths and applying a split-merge strategy~\cite{avgerinos2014enhancing,sen2015multise}.
  On \autoref{lst:example}, expanding the two tristate options and branching on the conditional spawns $3 \times 3 \times 2 = 18$ execution paths before merging, and each subsequent independent conditional can double the path count.
  By contrast, \tool{} maintains a single consolidated symbolic state in which \texttt{obj-y} and \texttt{obj-m} hold six guarded words in total, and each subsequent append adds only the new guarded words.
  MultiSE~\cite{sen2015multise} introduced value summaries to share symbolic expressions across paths without auxiliary variables, and Kmax~\cite{gazzillo2017kmax} similarly localizes configuration explosion to individual statements by tracking reaching configurations over complete strings.

  In summary, representing variables as sets of guarded words and merging states at conditional join points yields per-file build conditions at a cost proportional to the number of distinct words, enabling constraint-based reasoning over the build system.

\section{Approach}
  \label{sec:approach}

  \subsection{Symbolic State and Algorithm}
    \label{sec:approach:state}
    This subsection defines the symbolic state representation and the top-level worklist algorithm that traverses the Makefile hierarchy of a project.
    Let $M$ be a collection of Kbuild Makefiles and $c$ be a configuration that assigns values to the configuration options referenced in $M$.
    For each target object $o$, \tool{} computes a quantifier-free formula $\Phi_M(o)$, its build condition, such that evaluating $\Phi_M(o)$ under $c$ predicts whether Kbuild compiles $o$ under $c$.
    The symbolic state $\sigma$ is an abstract symbol table that maps each Make variable $n$ to a variational set of guarded words~\cite{walkingshaw2014variational}: an entry $w \mapsto \phi$ records that the word $w$ is a member of $n$ along all execution paths whose configuration satisfies the guard $\phi$, a Boolean formula over configuration options, analogous to a guarded symbolic expression in a value summary~\cite{sen2015multise}.
    We write $\sigma[n](w) = \bot$ when $w$ is absent from $\sigma[n]$, and we write $\sqcup$ for the value-summary union of two guarded word sets, which coalesces duplicate words by taking the disjunction of their guards and drops entries with unsatisfiable guards~\cite{sen2015multise}.
    Unlike value summaries over scalar variables whose guards are mutually exclusive, the guards of distinct words in $\sigma[n]$ may overlap because a single configuration can include multiple space-separated words in a Make variable.
    For an individual Makefile, \textsc{Exec} (\autoref{alg:exec}) evaluates its statements in a single pass starting from an empty symbolic state under the ambient guard $\top$; restricting a state to a guard $\delta$ conjoins $\delta$ with the guard of every word in the state.

    \begin{algorithm}[t]
    \caption{Build conditions of the objects of a source tree}\label{alg:extract}
    \KwIn{entry Makefiles $E$ with reachability guards, goal-definition prefixes $\Gamma$}
    \KwOut{map $\Phi$ from objects to build conditions}
    $R[m] \gets \bot$ for each Makefile $m$; $Q \gets E$; $\Phi[o] \gets \bot$ for each object $o$\;
    \While{$Q$ is nonempty}{\label{line:loop}
      remove $(m,\gamma)$ from $Q$\;
      $\delta \gets \gamma \land \neg R[m]$\;\label{line:delta}
      \lIf{$\delta$ is unsatisfiable}{\textbf{continue}}\label{line:skip}
      $S \gets$ state of $m$ after \textsc{Exec}, restricted to $\delta$\;\label{line:exec}
      $R[m] \gets R[m] \lor \gamma$\;\label{line:covered}
      \ForEach{subdirectory $d$ with guard $\eta$ in $S$}{
        add (Makefile of $d$, $\eta$) to $Q$\;\label{line:descend}
      }
      \ForEach{object $(o,\phi)$ selected by $S$ through $\Gamma$}{
        $\Phi[o] \gets \Phi[o] \lor \phi$\;\label{line:object}
      }
    }
    \Return $\textsc{Close}(\Phi)$\tcp*{objects that rules need}\label{line:close}
    \end{algorithm}

    \autoref{alg:extract} takes a project's entry Makefiles $E$ and goal-definition prefixes $\Gamma$, and returns the build-condition map $\Phi$.
    It maintains a worklist $Q$ of pairs $(m, \gamma)$, where $\gamma$ is the directory reachability guard under which Kbuild descends into Makefile $m$, together with a table $R[m]$ recording the disjunction of reachability guards already explored for $m$.
    In each iteration (\autoref{line:loop}), the algorithm dequeues $(m, \gamma)$, restricts attention to the unexplored configurations $\delta = \gamma \land \neg R[m]$ (\autoref{line:delta}), and skips the visit if $\delta$ is unsatisfiable (\autoref{line:skip}).
    Otherwise, it symbolically executes $m$ and restricts the resulting state $S$ to $\delta$ (\autoref{line:exec}), updates the explored guard $R[m]$ (\autoref{line:covered}), enqueues each subdirectory referenced in $S$ along with its guard (\autoref{line:descend}), and accumulates the build conditions of all objects selected via $\Gamma$ (\autoref{line:object}).
    When multiple Makefiles or directory routes select the same object $o$, the disjunction at \autoref{line:object} combines their conditions.
    For \autoref{lst:example}, the symbolic state $S$ after \autoref{line:exec} contains the guarded words of \texttt{obj-y} and \texttt{obj-m} from \autoref{tab:example} conjoined with the reachability guard of the \texttt{fs/ext4/} directory.


    \begin{algorithm}[t]
    \caption{\textsc{Exec}: symbolic execution of one statement}\label{alg:exec}
    \KwIn{statement $s$, state $\sigma$, ambient guard $g$}
    \KwOut{updated state $\sigma$}
    \uIf{$s$ is an assignment $x\ \mathit{op}\ e$}{
      $V \gets$ the words $w \mapsto \phi_w$ of $e$ (or $e \mapsto \top$ if the variable is recursively expanded)\;\label{line:rhs}
      \ForEach{name $n$ with guard $\psi_n$ in the expansion of $x$}{\label{line:lhs}
        $\psi \gets g \land \psi_n$\;
        \uIf{$\mathit{op}$ is an overwrite or $\sigma[n]$ is undefined}{
          $\sigma[n] \gets \{w \mapsto \psi \land \phi_w\} \sqcup \{w \mapsto \phi \land \neg\psi : (w \mapsto \phi) \in \sigma[n]\}$\;\label{line:overwrite}
        }
        \Else{
          $\sigma[n] \gets \sigma[n] \sqcup \{w \mapsto \psi \land \phi_w\}$\;\label{line:append}
        }
      }
    }
    \ElseIf{$s$ is a conditional with test $t$, then-arm $T$, else-arm $F$}{
      $\kappa \gets$ condition under which $t$ holds; $\sigma_t, \sigma_e \gets$ copies of $\sigma$\;\label{line:copy}
      $\textsc{Exec}(T,\sigma_t,g\land\kappa)$; $\textsc{Exec}(F,\sigma_e,g\land\neg\kappa)$\;
      \ForEach{name $n$ assigned in $T$ or $F$ and word $w$}{\label{line:mergeloop}
        \uIf{$\sigma_t[n](w) = \sigma_e[n](w) = \phi$}{$\sigma[n](w) \gets g \land \phi$\;\label{line:same}}
        \Else{$\sigma[n](w) \gets (g \land \kappa \land \sigma_t[n](w)) \lor (g \land \neg\kappa \land \sigma_e[n](w))$\;\label{line:merge}}
      }
    }
    \Return $\sigma$\;
    \end{algorithm}

  \subsection{Assignments}\label{sec:approach:assign}
  This subsection explains how \tool{} symbolically executes variable assignments, including runtime variable name construction, guarded updates on overwrites, and the two Make variable flavors.
  \autoref{alg:exec} evaluates each statement under an ambient guard $g$ representing the conjunction of enclosing branch conditions, which Kmax calls the reaching configuration~\cite{gazzillo2017kmax}.
  Because Make allows variable names on the left-hand side of an assignment to be computed dynamically via variable expansion, as in \texttt{obj-\$(CONFIG\_EXT4\_FS)}, \autoref{line:lhs} expands the left-hand expression $x$ into concrete variable names $n$ paired with their guards $\psi_n$: \texttt{obj-y} under $E_y$, \texttt{obj-m} under $E_m$, and \texttt{obj-} when the option is unset.
  A single assignment statement can thus update multiple target variables under different effective guards $\psi = g \land \psi_n$.
  An append assignment (\texttt{+=}) unions the right-hand guarded words into $\sigma[n]$, conjoining each word's guard $\phi_w$ with $\psi$ (\autoref{line:append}).
  An overwrite assignment (\texttt{:=} or \texttt{=}) replaces the variable's contents only on paths where $\psi$ holds: \autoref{line:overwrite} performs a guarded update~\cite{sen2015multise,gazzillo2017kmax} that assigns guard $\psi \land \phi_w$ to each new word while restricting every pre-existing word $(w \mapsto \phi) \in \sigma[n]$ to $\phi \land \neg\psi$.
  In \autoref{lst:example}, line~2 overwrites \texttt{obj-y} under $\psi = T_y$, strengthening the guard of \texttt{ext4.o} from $E_y$ to $E_y \land \neg T_y$.
  Conjoining $\neg\psi$ ensures that \texttt{ext4.o} is excluded under $E_y \land T_y$, matching concrete Make evaluation where the second assignment replaces the earlier value.


  \tool{} also models the two variable flavors in GNU Make, following the distinction in SYMake~\cite{tamrawi2012symmake} and Kmax~\cite{gazzillo2017kmax}.
  A simply-expanded variable (\texttt{:=}) evaluates its right-hand side immediately at assignment time.
  A recursively-expanded variable (\texttt{=}) stores its right-hand side verbatim and defers evaluation until the variable is referenced; accordingly, \tool{} stores an unexpanded expression when a recursive definition contains variable references (\autoref{line:rhs}) and expands deferred references in goal definitions after executing the Makefile.
  Linux's \texttt{drivers/xen/Makefile} illustrates why deferred expansion is needed: it appends \texttt{\$(xen-pad-y)} to \texttt{dom0-y} one line before defining \texttt{xen-pad-y}, so only expansion at reference time resolves \texttt{xen-acpi-pad.o}.

  \subsection{Expansion of Names and Words}\label{sec:approach:expand}
  This subsection describes how \tool{} lifts string concatenation, variable expansion, and file inclusion to sets of guarded words.
  In Make, the right-hand side of an assignment is whitespace-delimited into independent word expressions.
  Adjacent subexpressions within a single token, such as \texttt{\$(EXTRA).o} on line~8 of \autoref{lst:example}, are concatenated using a lifted cross-product operation~\cite{gazzillo2017kmax} that pairs each concrete string combination with the conjunction of their guards, yielding \texttt{verity.o} under $V$ and \texttt{crypto.o} under $\neg V$.
  Treating a whitespace-separated list such as \texttt{\$(a-y) \$(b-y) \$(c-y)} as a set of independent words avoids taking the cross product across the three variables, preserving each word's guard directly.
  When a variable reference may be undefined along some paths, \tool{} includes the empty string guarded by the negation of the variable's definedness condition, which is essential when the reference appears inside a word or list.
  For instance, Linux's \texttt{dvb-core} Makefile defines \texttt{dvb-net-\$(CONFIG\_DVB\_NET) := dvb\_net.o} and includes \texttt{\$(dvb-net-y)} in \texttt{dvb-core-objs}; retaining the empty alternative ensures that the remaining members of \texttt{dvb-core-objs} do not spuriously acquire a dependency on \texttt{CONFIG\_DVB\_NET}.
  Built-in text functions and substitution references such as \texttt{ixgbe-\$(CONFIG\_FCOE:m=y)} are lifted similarly by applying the string transformation to each word while preserving its guard.
  Finally, \tool{} inlines \texttt{include} directives whose target paths resolve statically and slices away variable assignments that cannot flow into goal definitions or build rules.

  \subsection{State Merging at Conditionals}\label{sec:approach:merge}
  This subsection presents how \tool{} evaluates conditional blocks and merges branch states at join points.
  For an \texttt{ifeq} or \texttt{ifneq} directive, \tool{} expands both operands and computes the branch guard $\kappa$ as the disjunction of conjunctions over matching (or non-matching) guarded words; for \texttt{ifdef} and \texttt{ifndef}, $\kappa$ is the disjunction of guards under which the variable has a non-empty definition~\cite{gazzillo2017kmax}.
  Chains of \texttt{else ifeq} directives are desugared into nested conditionals in the else-arm.
  To evaluate a conditional under ambient guard $g$, \tool{} clones the incoming state $\sigma$ into $\sigma_t$ and $\sigma_e$ (\autoref{line:copy}), executes the then-arm under $g \land \kappa$ and the else-arm under $g \land \neg\kappa$, and merges the resulting states at the confluence point (\autoref{line:merge}), following static state merging~\cite{kuznetsov2012efficient,avgerinos2014enhancing}.
  \tl{Kuznetsov et al. is not in the llmwiki; confirm the citation}
  Only variables modified in either branch are iterated over during the merge (\autoref{line:mergeloop}).
  In \autoref{lst:example}, the then-arm assigns \texttt{verity} under $V$ to \texttt{EXTRA} and the else-arm assigns \texttt{crypto} under $\neg V$, so the merged state maps \texttt{EXTRA} to both guarded words and execution proceeds with a single symbolic state.
  Whenever a word $w$ of a modified variable $n$ carries the identical guard $\phi$ in both branches, \tool{} simplifies its merged guard directly to $g \land \phi$ (\autoref{line:same}).
  This simplification is critical for scalability: in a Makefile with $k$ sequential conditionals that each append a distinct object to \texttt{obj-y}, preserving unchanged guards avoids wrapping every previously added word in $k$ nested case splits.

  \begin{proposition}\label{prop:merge}
  Let $\sigma'$ be the symbolic state that \autoref{alg:exec} produces after a conditional statement with branch guard $\kappa$ under ambient guard $g$.
  For every configuration $c$ satisfying $g \land \kappa$, $\sigma'$ evaluates to the same word set as the then-arm state $\sigma_t$, and for every configuration $c$ satisfying $g \land \neg\kappa$, $\sigma'$ evaluates to the same word set as the else-arm state $\sigma_e$.
  \end{proposition}

  \noindent
  \autoref{prop:merge} holds for the core calculus of assignments and conditionals in \autoref{alg:exec}, where word order and multiplicity are abstracted.
  The proof follows from \autoref{line:merge} by distributing evaluation under $c$ across the disjunction $(g \land \kappa \land \sigma_t[n](w)) \lor (g \land \neg\kappa \land \sigma_e[n](w))$; when $\sigma_t[n](w) = \sigma_e[n](w) = \phi$, factoring out $\phi$ yields $(g \land \kappa \lor g \land \neg\kappa) \land \phi \equiv g \land \phi$ (\autoref{line:same}).

  \subsection{Descending into Subdirectories}\label{sec:approach:dirs}
  This subsection describes how \tool{} tracks reachability guards across recursive directory traversal.
  In Kbuild, listing a directory in a goal definition, \eg, \texttt{obj-\$(CONFIG\_X) += sub/}, instructs Make to descend into \texttt{sub/} and evaluate \texttt{sub/Makefile}, paralleling the hierarchical directory structure of the source tree~\cite{gazzillo2017kmax}.
  \tool{} propagates the guard of the directory entry as the incoming reachability guard $\gamma$ for the child Makefile, so every object and subdirectory in the child inherits its parent's reachability constraint.
  A subdirectory Makefile can be reached along multiple directory routes.
  For instance, if a parent Makefile selects \texttt{a/} under guard $A$ and \texttt{b/} under guard $B$, and both \texttt{a/Makefile} and \texttt{b/Makefile} select \texttt{shared/}, then an object \texttt{x.o} unconditionally listed in \texttt{shared/Makefile} has the build condition $A \lor B$.
  Simply marking \texttt{shared/Makefile} as visited after traversing \texttt{a/} would miss the reachability path through \texttt{b/}.
  To handle multiple routes and cycles, \tool{} records for each Makefile $m$ the cumulative guard $R[m]$ of configurations already explored (\autoref{line:covered}); when $(m, \gamma)$ is dequeued, it computes the residual guard $\delta = \gamma \land \neg R[m]$ (\autoref{line:delta}).
  If $\delta$ is unsatisfiable, no new configurations reach $m$ and the entry is pruned (\autoref{line:skip}); otherwise, \tool{} evaluates $m$ under $\delta$ and disjoins $\gamma$ into $R[m]$.
  Consequently, any cyclic directory reference terminates as soon as its residual guard becomes unsatisfiable, and because both the set of Makefiles and the configuration space are finite, $R[m]$ can be weakened only finitely many times before the worklist empties.
  Because top-level project Makefiles primarily contain imperative build recipes and environment setup, \tool{} starts traversal from the entry Makefiles specified in the project settings (\autoref{sec:impl}).

  \subsection{From Words to Objects}\label{sec:approach:objects}
  This subsection details how \tool{} resolves the guarded words of goal definitions into compiled object files according to Kbuild's linking and prerequisite rules.
  While goal definitions specify which compilation units and composites are selected, Kbuild's canned build rules determine which physical \texttt{.o} files are emitted.
  \tool{} inspects variables whose names match the goal-definition prefixes (\eg, \texttt{obj-}, \texttt{lib-}) configured for the project, suffixed by \texttt{y}, \texttt{m}, or the empty suffix.
  When a goal definition selects a composite object $t$\texttt{.o}, Kbuild resolves its component member objects from the variables $t$\texttt{-y} and $t$\texttt{-objs}, and additionally from $t$\texttt{-m} when $t$ is built as a module.
  Each member object is compiled under the conjunction of its own membership guard and the build condition of the parent composite $t$, as illustrated by \texttt{inode-test.o} in \autoref{tab:example}.
  Composite expansion accounts for a large fraction of the kernel build: in Linux, 16,336 of the 32,829 extracted objects are members of composite objects.
  Beyond basic goal definitions and composites, \tool{} models three Kbuild semantics that govern object emission.

  \emph{Built-in composite objects.}
  When a composite object is selected via \texttt{obj-y} to be linked directly into the kernel image, Kbuild compiles its member objects and links them into the parent archive without emitting an intermediate $t$\texttt{.o} file; accordingly, \tool{} emits the composite object $t$\texttt{.o} itself only under the guard for which it is selected as a module via \texttt{obj-m}.

  \emph{Routes into directories.}
  Kbuild compiles the built-in (\texttt{obj-y}) objects of a subdirectory only when the subdirectory is reached through a chain of \texttt{obj-y} directory entries (tracked by Kbuild's internal \texttt{need-builtin} flag); if a parent Makefile enters the subdirectory solely via \texttt{obj-m}, only module targets in that subdirectory are built.
  \tool{} therefore tracks separate built-in and module reachability guards for each Makefile.

  \emph{Rule prerequisites.}
  Certain object files, such as linker scripts, generated offsets, and boot stubs, are never listed in goal definitions and are compiled solely because an explicit Makefile rule or sub-make command depends on them.
  During symbolic execution, \tool{} records explicit rules (mapping expanded targets to prerequisites under their ambient guards~\cite{gazzillo2017kmax,tamrawi2012symmake}) as well as sub-make invocations that specify a target directory and goal; after worklist traversal, \textsc{Close} (\autoref{line:close}) computes the transitive closure of prerequisites starting from all selected objects and top-level link targets such as \texttt{vmlinux.o}.

  \subsection{Using Build Conditions}\label{sec:approach:use}
  This subsection describes how \tool{} formulates developer build queries as SMT constraint-solving problems over the extracted build conditions.
  Because each build condition $\Phi_M(o)$ is a quantifier-free first-order formula over symbolic configuration options, reasoning about when an object is built reduces to evaluating or solving $\Phi_M(o)$ with an SMT solver~\cite{nguyen2020kbuild}.
  The \texttt{why} command takes an object file and a concrete \texttt{.config}, evaluates $\Phi_M(o)$ under that configuration's option assignments, and reports both the resulting build status and a condition chain highlighting which option clauses in $\Phi_M(o)$ are violated.
  The \texttt{config-for} command takes a commit or patch, maps the modified C and assembly source files to their corresponding target objects, conjoins their build conditions with the Kconfig feature-model constraints for the relevant options, and queries the SMT solver for a satisfying configuration that minimizes the number of option changes relative to a baseline \texttt{.config}.
  If two modified files require mutually exclusive configuration settings, the conjunction is unsatisfiable and \tool{} partitions the targets into compatible groups so each can be tested in a separate build.

  \subsection{Meaning of a Build Condition}\label{sec:approach:meaning}
  This subsection states the domain encoding of configuration options and the soundness boundaries of the extracted build conditions.
  Each symbolic configuration option ranges over the values declared by its Kconfig type: a Boolean option ranges over $\{\texttt{y}, \text{unset}\}$, while a tristate option ranges over $\{\texttt{y}, \texttt{m}, \text{unset}\}$ and conjoins the global module-support constraint \texttt{CONFIG\_MODULES=y} with every \texttt{=m} guard.
  An extracted build condition $\Phi_M(o)$ is a static approximation of Kbuild's concrete behavior: \tool{} models the Kbuild subset of GNU Make shown in \autoref{tab:scope} and initiates traversal from the declared entry Makefiles, leaving arbitrary shell recipes and top-level orchestration rules outside the analysis.
  Moreover, $\Phi_M(o)$ captures the constraints encoded in Kbuild Makefiles alone; Kconfig inter-option dependencies (\texttt{depends on}, \texttt{select}, and \texttt{choice} blocks) are conjoined separately during solver queries (\autoref{sec:approach:use}).
  Consequently, any satisfying assignment produced by the SMT solver is treated as a candidate configuration that must be validated by running the Kconfig configurator and executing a concrete build, as evaluated in \autoref{sec:eval}.

\section{Implementation}\label{sec:impl}

This section describes the implementation of \tool{}, its project configuration format, and its command-line analyses.
\tool{} is implemented in Python.
Following Kmax~\cite{gazzillo2017kmax} and Nguyen and Nguyen~\cite{nguyen2020kbuild}, it parses Makefiles into abstract syntax trees (ASTs) using \texttt{pymake3}, our Python~3 port of the Mozilla \texttt{pymake} parser, and represents guards and build conditions as quantifier-free formulae in the Z3 SMT solver~\cite{demoura2008z3}.
Each configuration option is encoded as a finite enumeration sort in Z3 over two values ($\{\texttt{y}, \text{unset}\}$ for the Boolean domain) or three values ($\{\texttt{y}, \texttt{m}, \text{unset}\}$ for projects that enable the tristate domain).
Guards are constructed from equality predicates over these option sorts using logical conjunction, disjunction, and negation, and \tool{} simplifies each formula eagerly after every Boolean operation~\cite{sen2015multise}.

During worklist traversal (\autoref{alg:extract}), \tool{} queries Z3 to check guard satisfiability, prune infeasible directory routes, and restrict child states.
To avoid redundant parsing and evaluation when a subdirectory Makefile is reached along multiple routes, \tool{} serializes the post-execution symbolic state of each Makefile---together with its recorded explicit rules---into a disk cache keyed by canonical file path; a subsequent visit under a new residual guard $\delta$ loads the cached state and conjoins $\delta$ directly (\autoref{line:exec} of \autoref{alg:extract}).
Because a Makefile can be re-evaluated under multiple residual guards across the directory hierarchy, the number of Makefile instances processed during a full-tree analysis can exceed the number of distinct Makefile files in the source tree.
Alongside the build conditions, \tool{} records provenance metadata for each target object: the contributing Makefiles, goal definitions, and explicit rules, as well as the \texttt{include} directives resolved or left unresolved and any Makefiles that failed to parse.

Project-specific settings specify the entry Makefiles and Kbuild conventions of \autoref{sec:approach:dirs} and \autoref{sec:approach:objects}.
Each project configuration declares the top-level entry directories (each optionally guarded by an enabling configuration option), the entry build goals, the recognized goal-definition prefixes and their aliases, fixed variable bindings such as \texttt{SRCARCH=x86}, the top-level link targets, the option domain (Boolean or tristate), and toggles for the three Kbuild linking semantics of \autoref{sec:approach:objects}.
We extract these declarations directly from each project's top-level Makefiles and annotate every entry with the source lines from which it is derived.
For Linux x86, the project configuration specifies ten entry directories (three of them conditionally guarded), two entry goals, and fixed bindings for the architecture variables \texttt{SRCARCH} and \texttt{BITS}~\cite{gazzillo2017kmax}.

\tool{} provides a command-line interface that answers the developer queries of \autoref{sec:approach:use} over a cached whole-tree analysis.
The whole-tree cache stores the build condition, target classification, and provenance of every extracted object; it is keyed by a cryptographic digest of the analyzer source and project settings, and tracks the timestamps of all read Makefiles and included files so that modifying any build file automatically invalidates the cache.
Given an object file and a concrete \texttt{.config}, the \texttt{why} command reports a condition chain that traces the directory reachability route to the object's Makefile, the goal definition or composite object that selects the file, and the truth value of each clause under the given \texttt{.config}.
When an object is omitted from the build, \texttt{why} pinpoints the first falsified conjunct in the condition chain and lists the configuration options responsible.

For the \texttt{config-for} command, \tool{} constructs a Kconfig feature model $K$ using \texttt{kconfiglib} (extended to parse newer Kconfig syntax) and slices $K$ to the cone of influence of the options referenced in the touched objects' build conditions.
In $K$, each option is bounded above by its \texttt{depends on} constraints and below by incoming \texttt{select} clauses, and an option may be enabled only when activated by a \texttt{select}, an \texttt{imply}, a visible user prompt, or an active \texttt{default} attribute.
Because $K$ abstracts away the priority order among multiple active defaults, it over-approximates the set of valid Kconfig assignments.
When invoked with verification enabled, \texttt{config-for} writes the solver's candidate assignment as a configuration fragment, runs the kernel configurator (\texttt{make olddefconfig}) to materialize a valid \texttt{.config}, and verifies both that the requested option settings are preserved and that \tool{} predicts every target object under the resulting configuration.
Finally, the \texttt{blindspots} command evaluates the extracted build conditions across a corpus of configurations and reports build-system blind spots---source files that remain uncompiled under every configuration in the corpus---grouped by their subsystem entries in \texttt{MAINTAINERS}.
The implementation of \tool{} and all evaluation scripts are available in the anonymized artifact.

\section{Evaluation}\label{sec:eval}

We evaluate \tool{} to determine how accurately its build conditions predict the object files produced by concrete builds, how its consolidated state representation scales relative to path-forking symbolic execution and Kmax, how effectively its build conditions support developer maintenance tasks, and how each component of its design contributes to accuracy.
Specifically, we investigate four research questions:
\begin{description}
\item[RQ1 (Build Agreement)] When the extracted build conditions are evaluated under concrete configurations, how accurately do the predicted object sets match the ground-truth object files compiled by full builds?
\item[RQ2 (Scalability)] How do the running time and memory consumption of \tool{} scale with the number of conditional assignments compared with path-forking symbolic execution and Kmax, and what is the cost of analyzing entire project trees?
\item[RQ3 (Developer Tasks)] Can the extracted build conditions explain why source files are included or excluded in a build, synthesize valid configurations to compile files modified by real-world commits, and identify uncompiled blind spots across standard configurations?
\item[RQ4 (Comparison and Ablation)] How does \tool{} compare with Kmax in build agreement on the same concrete builds, and how much do \texttt{include} inlining, rule closure, and Kbuild link semantics contribute to \tool{}'s precision and recall?
\end{description}

\subsection{Experimental Setup}\label{sec:setup}

\emph{Subjects.}
\autoref{tab:subjects} summarizes the five open-source Kbuild systems and concrete configurations used in our evaluation: Linux 7.2.8, BusyBox 1.38.0, Barebox 2026.09.0, Das U-Boot 2026.07, and coreboot 26.06.
Linux and BusyBox are the two benchmark systems evaluated by Kmax~\cite{gazzillo2017kmax} and Nguyen and Nguyen~\cite{nguyen2020kbuild}, allowing a direct comparison on established subjects.
Barebox, Das U-Boot, and coreboot are widely used bootloader and firmware codebases whose Kbuild dialects introduce stage-specific goal-definition prefixes (\eg, for secondary program loaders and ROM stages), testing whether \tool{} generalizes across Kbuild variants~\cite{gazzillo2017kmax}.
Each subject tree is unpacked from an official release tarball and verified against its published SHA-256 checksum where available (Linux, BusyBox, and coreboot).
For BusyBox, we run \texttt{make gen\_build\_files} before analysis because BusyBox generates several of its Kbuild Makefiles from templates during build preparation.
For Linux, we evaluate four representative configurations that span the configuration space: \texttt{tinyconfig} (i386) and \texttt{allmodconfig} (x86-64) represent the minimal and maximal kernel builds, \texttt{defconfig} is the standard default x86-64 kernel configuration, and the Debian x86-64 configuration represents a production distribution kernel~\cite{nguyen2020kbuild}.
Each of the remaining four subjects is evaluated on its standard default or sandbox configuration.

\emph{Ground-Truth Builds.}
Following Nguyen and Nguyen~\cite{nguyen2020kbuild}, we establish ground truth for each configuration $c$ by running a clean concrete build and recording the compiled \texttt{.o} object files.
Each configuration is built from scratch with \texttt{make -k -j8}, where \texttt{-k} instructs Make to continue compiling independent targets past any individual compile error so that the ground-truth inventory is complete.
Build times range from 2.6 minutes for Linux \texttt{tinyconfig} to 100.2 minutes for Linux \texttt{allmodconfig}.
The ground-truth object set $B_c$ for configuration $c$ comprises all \texttt{.o} files emitted in the build tree, excluding the post-processing \texttt{*.mod.o} stubs generated by \texttt{modpost}.

We modify stock configurations only when required by the host toolchain or missing external assets:
in the Debian kernel configuration, we clear the trusted and revocation key-path strings because Debian's signing certificates are external to the upstream kernel tree, and \texttt{olddefconfig} drops four Debian-specific patch options;
in Linux \texttt{allmodconfig}, we disable \texttt{WERROR}, \texttt{DRM\_WERROR}, and \texttt{DRM\_AMDGPU\_WERROR} so warnings under GCC~16.2 do not abort compilation;
in coreboot, we set \texttt{CONFIG\_PAYLOAD\_NONE=y} to avoid cloning the external SeaBIOS repository during the build;
and in U-Boot, we pass \texttt{NO\_PYTHON=1} because its device-tree Python wrapper invokes removed Python~2 APIs, which causes only the final \texttt{binman} image-packaging step to fail after all object files have been compiled.
In BusyBox, \texttt{networking/tc.c} fails to compile against modern Linux kernel headers; we record such compile-time failures---along with downstream targets identified via \texttt{make -n} that Make skipped due to a failed prerequisite---separately from analysis false positives.

\emph{Metrics.}
For a subject codebase, \tool{} extracts a universe $U$ of target objects and maps each object $o \in U$ to its build condition $\Phi_M(o)$.
Substituting the concrete option settings of a configuration $c$ into each condition yields the predicted object set $P_c = \{o \in U \mid c \models \Phi_M(o)\}$.
When evaluating $\Phi_M(o)$ under $c$, any option that is omitted from \texttt{.config} or marked ``\texttt{is not set}'' takes the value unset; the Linux analysis uses the tristate option domain.
Comparing the predicted set $P_c$ against the ground-truth build inventory $B_c$, we measure true positives $TP = |P_c \cap B_c|$, false positives $FP = |P_c \setminus B_c|$, in-universe false negatives $FN_U = |(B_c \cap U) \setminus P_c|$, and out-of-universe built objects $O = |B_c \setminus U|$.
From these counts we report precision $TP / (TP + FP)$ and overall build overlap $TP / |B_c|$.
Whereas $FN_U$ measures imprecision in the symbolic execution of extracted Makefiles (extracted objects whose build condition evaluated to false despite being built), the overlap metric $TP / |B_c|$ penalizes the analysis for every built object outside the extracted universe $U$, such as arch-specific boot payloads under \texttt{arch/x86/boot/} invoked via top-level \texttt{bzImage} recipes.

\emph{Baselines and Ablations.}
We compare \tool{} against Kmax~\cite{gazzillo2017kmax} (\texttt{kmaxall} v4.10) on Linux and BusyBox by evaluating Kmax's extracted Boolean conditions under the same concrete configurations and scoring them against $B_c$ using the same metrics.
In RQ2, we evaluate scalability on synthetic Kbuild Makefiles containing $k$ independent conditional blocks, comparing \tool{} against a conventional path-forking symbolic executor (which forks a symbolic state at each conditional branch~\cite{nguyen2020kbuild}) and against Kmax.
In RQ4, we conduct an ablation study that disables three design components of \tool{} one at a time: static \texttt{include} inlining (\texttt{no\_includes}), transitive prerequisite closure over explicit rules (\texttt{no\_rules}), and the three Kbuild linking and reachability rules of \autoref{sec:approach:objects} (\texttt{no\_link\_semantics}).

\emph{Experimental Environment.}
All static analyses and concrete builds were executed on a workstation equipped with an Intel Core i7-7700 CPU (8 logical cores) and 31\,GiB of RAM running Debian GNU/Linux, with Python 3.14.7, Z3 5.1.0, GNU Make 4.4.1, and GCC 16.2.0.
Linux configurations that enable Rust support were compiled with \texttt{rustc} 1.95.0 and \texttt{bindgen} 0.72.1, and coreboot was compiled using its bundled i386 cross-compilation toolchain.
Each static analysis run executes as a single-threaded process.
For whole-tree performance measurements, we run each tool three times per subject on an idle system (load average below 1.0) and report the median wall-clock running time and peak resident set size (RSS).
