=== CONTEXT C1: Existing tool: klocalizer/krepair/koverage (Kmax suite) already solves config-for and patch coverage
existing: Kmax, klocalizer, krepair, koverage, KBuildMiner, GOLEM, Vampyr, Nguyen & Nguyen.
gap: A head-to-head on the same patches. Object-level exactness, explanation chains (why), MAINTAINERS-grouped blindspots, speed (kclause 2-3 min, kmax 10-15 min), non-Linux Kbuild trees.
fit: Not a problem but a competitor: it overlaps with config-for and the why side of coverage, while blindspots/why chains and the multi-project scope are the stated non-overlaps (claim 138 says these were not found, not that they are absent).

[82] (existing_tool/tool, 2024-07) krepair is the closest existing tool to kfold's config-for: it uses Kbuild constraints (via kmax) plus Kconfig constraints and a theorem prover to repair an existing config so a patch is built; 98.5% avg coverage, 97% of patches need one config, found 18 build errors (2 not yet fixed, one patch accepted). Stated limits (as reported by fetch extraction of the paper): only build-system constraints, header-only patches unsupported, run-time (C) uses of options unsupported, evaluated on one system, up to 23 configs in worst case. kfold overlap is high for config-for; differentiator is per-object condition output and explanation.

[109] (existing_tool/tool, n.d.) klocalizer/krepair (part of the kmax suite) already takes a config that fails to build a patch's lines and repairs it so the whole patch builds. It also accepts a target object (--include foo.o), uses SuperC to collect #ifdef constraints inside source files, and emits several configs (NUM-ARCH.config) when a patch touches both arms of an #ifdef. It can also export the Kbuild/Kconfig constraints as DIMACS or SMT (--save-dimacs, --save-smt). This is the closest competitor to kfold's config-for command. Unlike kfold, klocalizer also models #ifdefs in source files.
    quote: "take a config file that fails to build lines of a patch and repairs it to build the whole patch"

[110] (existing_tool/tool, n.d.) The kmax GitHub repository is the home of the suite (kmax/kextract, klocalizer, krepair, koverage, kismet). [111] (statistic/statistic, 2024-04-27 (arXiv); FSE 2024) krepair evaluation (FSE 2024): 507 random patches sampled from about 71,000 mainline patches (2021-09-19 to 2022-09-18). Mean patch coverage was 98.5% for krepair-repaired defconfig, 88.5% for allyesconfig, 21.7% for defconfig and 29.2% for a single randconfig. Fewer than 1.53% of defconfig options changed for 99% of patches. allyesconfig builds take about 4 hours versus about 20 minutes for defconfig or repaired configs (10.5x faster). krepair runtime is a few minutes for most runs. A kfold evaluation must compare against these numbers.
    quote: "98.5% on average"
    source: Maximizing Patch Coverage for Testing of Highly-Configurable Software without Exploding Build Times | Yildiran, Oh, Lawall, Gazzillo | FSE 2024 / PACMSE (DOI 10.1145/3643746), arXiv 2404.17966 | https://arxiv.org/html/2404.17966
    candidate_problem: Per-patch config coverage; baseline numbers a competing approach must beat

[112] (counter_evidence/statistic, n.d.) krepair's own stated limitations show what stays open. It collects constraints only from the build system and Kconfig, and does not model C-level conditionals. Header-only patches (about 2% of patches) are unsupported and handled only by a heuristic. Cross-compilation depends on make.cross, which lacked loongarch, and 7 patches could not be built because of toolchain problems. The paper reports no accuracy measurement for the Kbuild constraints. These are gaps a precise per-object condition engine could target, such as an exact object-level semantic model with explanations. Note that the 'only collect constraints from the build system' remark in the paper's reasons-for-uncovered-lines list is a tool-limit statement.
    quote: "Header-only patches: These are unsupported"
    source: Maximizing Patch Coverage ... (krepair) |  | arXiv 2404.17966 (fetch summarized by tool; the quote is a paraphrased list item, so verify in the PDF) | https://arxiv.org/html/2404.17966
    candidate_problem: Open gaps in config-for-patch: header-only patches, constraint accuracy unvalidated, multi-arch toolchains

[114] (existing_tool/tool, n.d.) koverage (in the kmax suite) checks how much of a patch a given .config covers, using --check-patch, --config and --arch. It reports at line level. kfold's 'why OBJ --config .config' answers a similar question at object level and adds a condition chain as the explanation.
    quote: "check how much of patch is covered by a given config file"
    source: kmax (PyPI) |  | PyPI | https://pypi.org/project/kmax/
    candidate_problem: Explain/measure whether a given config builds a patch

[115] (existing_tool/tool, 2017-08) Kmax (Gazzillo, ESEC/FSE 2017) is a family-based static analysis of Kbuild Makefiles: paths are Boolean expressions over configuration options and variable state is tracked across configurations. It claims to be the first tool to collect all source files and their configurations from Linux. Slides report 1,985 Kbuild Makefiles controlling 19,651 C files, 1-2k more C files than earlier heuristics, and a mean x86 runtime of 84.15 s versus 45 s for KBuildMiner and about 3.4 h for GOLEM. Kmax is the direct ancestor of kfold, so the novelty claim against it has to be stated carefully.
    quote: "first tool to collect all source files and their configurations from Linux"
    source: Kmax: Finding All Configurations of Kbuild Makefiles Statically | Paul Gazzillo | ESEC/FSE 2017 (DOI 10.1145/3106237.3106283); figures came from search summaries of the paper and slides (https://www.paulgazzillo.com/papers/esecfse17_slides.pdf), since the PDF text was unreadable | https://paulgazzillo.com/papers/esecfse17.pdf
    candidate_problem: Prior art for extracting per-file build conditions from Kbuild

[116] (statistic/statistic, n.d.) Kmax paper claim that earlier studies of the x86 Linux 2.6.33.3 kernel counted at most 7,691 C files, while Kmax found 9,044, about 17% more. This is evidence that heuristic Kbuild parsers miss a material share of files.
    quote: "9,044"
    source: Kmax: Finding All Configurations of Kbuild Makefiles Statically |  | ESEC/FSE 2017 (figure from a search-result summary; verify in the PDF) | https://paulgazzillo.com/papers/esecfse17.pdf
    candidate_problem: Heuristic Kbuild extraction misses files

[117] (existing_tool/tool, n.d.) KBuildMiner (Nadi and Holt, 'Mining Kbuild to Detect Variability Anomalies in Linux', CSMR 2012) uses a fuzzy parser over Makefiles to collect compilation units. It is fast (mean 45 s on Linux, per the Kmax slides). The Kmax paper says it misses names built by concatenation or function calls and needs some Kbuild files hand-modified to fit the parser. It is not fully reliable.
    quote: "parses Kbuild files only heuristically, so it is not fully reliable"
    source: An Empirical Study of Configuration Mismatches in Linux (El-Sharkawy, Krafczyk, Schmid) |  | SPLC 2017 / arXiv 2110.05828. KBuildMiner paper page: https://ieeexplore.ieee.org/document/6178858/ | https://arxiv.org/pdf/2110.05828
    candidate_problem: Heuristic Kbuild parsing is unreliable

[118] (existing_tool/tool, 2012) GOLEM (Dietrich, Tartler, Schroeder-Preikschat, Lohmann, SPLC 2012) extracts variability by exploiting the build system itself rather than parsing it as text. It states that more than 65% of Linux features are handled by the build system and that it works across all Linux git-history versions and architectures. It is slow: the 2021 mismatch study chose KBuildMiner because it runs in under a minute versus about 90 minutes for GOLEM. Kmax slides give about 3.4 h.
    quote: "more than 65 percent of all features are actually handled by the build system"
    source: A Robust Approach for Variability Extraction from the Linux Build System | Dietrich, Tartler, Schroeder-Preikschat, Lohmann | SPLC 2012 (pp. 21-30). The quoted abstract content came from a search-result summary (https://cris.fau.de/publications/118556064/). | https://www.i4copter.cs.fau.de/Publications/2012/dietrich_12_splc.pdf
    candidate_problem: Prior art for Kbuild variability extraction

[119] (existing_tool/tool, n.d.) Vampyr (Hengelein and Lohmann, LPC 2014) is an undertaker-based driver for configuration-aware compile-testing of single files or batches. It generates a set of partial configurations that cover each #ifdef block and passes the results to gcc, clang or sparse (-C, -b batch mode). Undertaker 1.2 added coverage generation of partial Kconfig configurations. Vampyr works at the #ifdef block level, which kfold does not, but depends on its extracted Kconfig model. The authors say they prefer false negatives over false positives.
    quote: "Generate partial (Kconfig) configurations to cover each conditional block"
    source: undertaker announcement; Vampyr LPC 2014 talk |  | LWN; talk: https://blog.linuxplumbersconf.org/2014/ocw/system/presentations/2313/original/hengelein.pdf; changelog: https://lkml.iu.edu/hypermail/linux/kernel/1410.1/02846.html (undertaker 1.6, 2014). Not maintained recently as far as I saw, but I did not check. | https://lwn.net/Articles/456849/
    candidate_problem: Config-aware compile testing for #ifdef coverage; competitor at the intra-file level

[124] (existing_tool/tool, 2020) Nguyen and Nguyen, 'Using Symbolic Execution to Analyze Linux KBuild Makefiles' (ICSME 2020, pp. 712-716, per DBLP) is the closest prior art to kfold's approach.     quote: "Using Symbolic Execution to Analyze Linux KBuild Makefiles"

    candidate_problem: Prior art on symbolic execution of Makefiles

[138] (counter_evidence/tool, n.d.) Hostile verdict on the klocalizer comparison. It already solves 'find a config for a patch or file': it minimizes config change, handles the #ifdef constraints that kfold ignores, and reports 98.5% mean patch coverage on 507 patches. It is open source, on PyPI at version 4.10, and has been used by others (KBootRepair). It is maintained by a university group that also runs kismet, which the test robot uses. What it does not demonstrably do: (a) its Kbuild constraint accuracy is not reported in the FSE paper; (b) header-only patches are unsupported (about 2%); (c) it has no maintainers-grouped 'blindspots' report; (d) it has no 'why is OBJ not built' explanation chain; (e) it works through SuperC with a heavy setup, and one invocation covers one architecture; (f) it does not target BusyBox, Barebox, U-Boot or coreboot. I did not find evidence of these last points being claimed. kfold's differentiators would have to be (c), (d) and speed or exactness at object level, validated against klocalizer on the same patches.
    quote: "Repair usually covers all lines of a patch"
    source: Synthesis of kmax PyPI/README and the krepair paper (https://arxiv.org/html/2404.17966) |  | Own analysis from the cited sources. The points about what klocalizer does not do are inferences from absence in those pages, not stated in them. | https://pypi.org/project/kmax/
    candidate_problem: What klocalizer already solves versus what remains open
