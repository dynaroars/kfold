=== PROBLEM P2: Find a .config that builds a given file or patch, with minimal change to a base config (H2)
who: Patch authors, maintainers, reviewers, KUnit/test authors, embedded integrators, kernel researchers
strength: Strong demand evidence (checklist burden, academic motivation, forum threads). Direct prior art exists, so novelty is the issue. Independent sources: kernel docs, Yocto list, Arch forum, KUnit docs. Adoption of klocalizer is not visible on LKML or forums (17, 168). Only the kismet part of the kmax suite is confirmed to be in 0-day (27, 197).
existing: klocalizer/krepair/koverage (kmax suite, FSE 2024); undertaker/Vampyr (stale, about Linux 3.2); merge_config.sh; localmodconfig; kernelconfig.io; menuconfig search.
gap: Gaps the claims state for klocalizer: no accuracy validation of its Kbuild constraints (it says the formulas may be inexact), composite-object and CONFIG_BROKEN handling, one architecture per invocation, heavy SuperC/Java setup, header-only patches unsupported, constraint collection 2-15 minutes (274). No explanation chain. Non-Linux Kbuild trees are not targeted. kfold must be benchmarked head-to-head on the same patches.
fit: object-selection - This is the core of config-for. The fit is real but not novel: klocalizer already solves the problem at finer (line) granularity. Differentiation must rest on speed, exactness of Kbuild semantics, explanations, and other Kbuild trees.

--- supporting claims
[52] (need/anecdote, 2022-06-22) Slides state it is hard just to figure out which config options must be set for a .config to cover a commit; the build system (Kconfig + Kbuild Makefiles + C preprocessor) selects the code, and the .config must satisfy both Makefile options (obj-$(CONFIG_ARM_GIC) += irq-gic.o) and #ifdef options. Note: krepair covers Kbuild Makefile AND #ifdef conditions at line level; kfold covers only the Makefile part.
    quote: "hard just to figure out what config options need to be set so that your .config file covers a commit"
    source: Krepair slides, slides 17-19 | Paul Gazzillo, Necip Yildiran | Open Source Summit North America 2022 | https://paulgazzillo.com/files/oss2022.pdf
    candidate_problem: Patch-to-config derivation; overlaps with existing tool krepair, so differentiation must be on object-level precision, explanations (why), and reuse of the same conditions for other tasks.

[53] (existing_tool/tool, 2024) FSE 2024 krepair paper (same authors plus Oh, Lawall): single randconfig gives 29.2% average patch coverage, defconfig 21.7%, allyesconfig 88.5%, krepair on defconfig 98.5% while keeping build about 10x faster than allyesconfig; in Intel 0-day's 36,115 build-test reports, 63% used randconfig, 15% allyesconfig, 7% defconfig; sample of 507 patches out of about 71,000. Direct prior art for 'config-for PATCH'.
    quote: "a single random configuration file only achieves 29.2% patch coverage on average"
    source: Maximizing Patch Coverage for Testing of Highly-Configurable Software without Exploding Build Times | Yildiran, Oh, Lawall, Gazzillo | arXiv (FSE 2024 paper) | https://arxiv.org/html/2404.17966v1
    candidate_problem: config-for PATCH is already addressed by krepair (line-level, incl. #ifdef); kfold must show an advantage (object-level, Kbuild-semantics fidelity, explainability, speed).

[80] (pain_point/anecdote, 2024-07) Motivating example in the krepair paper: to build one file a developer must trace selects/depends across several Kconfig files (ARM_GIC cannot be selected directly; reachable via ARM_GIC_PM which depends on PM), and the Makefile condition alone does not guarantee the changed lines (under #ifdef/#else) are built. Concrete evidence that developers cannot easily explain or achieve 'why is this object/line built'.
    quote: "it is necessary to trace across multiple Kconfig files to discover that this option can be selected"
    source: Maximizing Patch Coverage for Testing of Highly-Configurable Software without Exploding Build Times | Yildiran, Oh, Lawall, Gazzillo | FSE 2024 (section 2.3) | https://arxiv.org/abs/2404.17966
    candidate_problem: Developer cannot explain why an object is or is not built (why)

[82] (existing_tool/tool, 2024-07) krepair is the closest existing tool to kfold's config-for: it uses Kbuild constraints (via kmax) plus Kconfig constraints and a theorem prover to repair an existing config so a patch is built; 98.5% avg coverage, 97% of patches need one config, found 18 build errors (2 not yet fixed, one patch accepted). Stated limits (as reported by fetch extraction of the paper): only build-system constraints, header-only patches unsupported, run-time (C) uses of options unsupported, evaluated on one system, up to 23 configs in worst case. kfold overlap is high for config-for; differentiator is per-object condition output and explanation.
    quote: "We describe the 18 build errors found by repaired configuration files"
    source: Maximizing Patch Coverage for Testing of Highly-Configurable Software without Exploding Build Times | Yildiran, Oh, Lawall, Gazzillo | FSE 2024 | https://arxiv.org/abs/2404.17966
    candidate_problem: Overlap with config-for (patch-covering config search)

[84] (need/anecdote, 2011-10) Open problem stated: a Linux developer who modified files wants to be sure every edited line compiles before submitting a patch, but finding the covering configurations is tedious by hand. Same paper reports some files (kernel/sched_fair.c) need seven configs and that more than 90% of files reach full #ifdef coverage with at most two configs.
    quote: "a sometimes difficult, but always tedious and error-prone task"
    source: Configuration Coverage in the Analysis of Large-Scale System Software | Tartler, Lohmann, Dietrich, Egger, Sincero | PLOS 2011 / SIGOPS OSR 2012 | https://sigops.org/s/conferences/sosp/2011/workshops/plos/02-tartler.pdf
    candidate_problem: Patch not built by any standard config (config-for)

[86] (pain_point/anecdote, 2011-10) Kconfig expansion of partial configs is fragile: Kconfig can silently drop requested options rather than report conflicts. Relevant to config-for which depends on a Kconfig model to realize solutions.
    quote: "Kconfig in some cases silently overwrites user choices instead of signaling incompatible item selections"
    source: Configuration Coverage in the Analysis of Large-Scale System Software | Tartler et al. | PLOS 2011 / SIGOPS OSR 2012 | https://sigops.org/s/conferences/sosp/2011/workshops/plos/02-tartler.pdf
    candidate_problem: Producing a valid .config that actually builds target objects (config-for)

[109] (existing_tool/tool, n.d.) klocalizer/krepair (part of the kmax suite) already takes a config that fails to build a patch's lines and repairs it so the whole patch builds. It also accepts a target object (--include foo.o), uses SuperC to collect #ifdef constraints inside source files, and emits several configs (NUM-ARCH.config) when a patch touches both arms of an #ifdef. It can also export the Kbuild/Kconfig constraints as DIMACS or SMT (--save-dimacs, --save-smt). This is the closest competitor to kfold's config-for command. Unlike kfold, klocalizer also models #ifdefs in source files.
    quote: "take a config file that fails to build lines of a patch and repairs it to build the whole patch"
    source: kmax (PyPI, latest 4.10, Aug 18 2026) |  | PyPI | https://pypi.org/project/kmax/
    candidate_problem: Find a .config that builds the objects/lines touched by a patch

[110] (existing_tool/tool, n.d.) The kmax GitHub repository is the home of the suite (kmax/kextract, klocalizer, krepair, koverage, kismet). The README describes klocalizer in patch mode and koverage (--check-patch, --config, --arch) and kismet. As shown: 72 stars, 29 forks, 1,289 commits, 77 open issues. This is a research-grade tool with modest adoption. The README lists these limits: some lines are still omitted (dead code, header files), setup needs SuperC with Java dependencies, and a full kismet run on x86_64 takes about an hour. Examples run one architecture per invocation (-a x86_64 or -a arm).
    quote: "some lines may still be omitted, for instance if they are dead code or in header files"
    source: paulgazz/kmax README |  | GitHub | https://github.com/paulgazz/kmax
    candidate_problem: Adoption and limits of the incumbent config-for-patch tool

[112] (counter_evidence/statistic, n.d.) krepair's own stated limitations show what stays open. It collects constraints only from the build system and Kconfig, and does not model C-level conditionals. Header-only patches (about 2% of patches) are unsupported and handled only by a heuristic. Cross-compilation depends on make.cross, which lacked loongarch, and 7 patches could not be built because of toolchain problems. The paper reports no accuracy measurement for the Kbuild constraints. These are gaps a precise per-object condition engine could target, such as an exact object-level semantic model with explanations. Note that the 'only collect constraints from the build system' remark in the paper's reasons-for-uncovered-lines list is a tool-limit statement.
    quote: "Header-only patches: These are unsupported"
    source: Maximizing Patch Coverage ... (krepair) |  | arXiv 2404.17966 (fetch summarized by tool; the quote is a paraphrased list item, so verify in the PDF) | https://arxiv.org/html/2404.17966
    candidate_problem: Open gaps in config-for-patch: header-only patches, constraint accuracy unvalidated, multi-arch toolchains

[138] (counter_evidence/tool, n.d.) Hostile verdict on the klocalizer comparison. It already solves 'find a config for a patch or file': it minimizes config change, handles the #ifdef constraints that kfold ignores, and reports 98.5% mean patch coverage on 507 patches. It is open source, on PyPI at version 4.10, and has been used by others (KBootRepair). It is maintained by a university group that also runs kismet, which the test robot uses. What it does not demonstrably do: (a) its Kbuild constraint accuracy is not reported in the FSE paper; (b) header-only patches are unsupported (about 2%); (c) it has no maintainers-grouped 'blindspots' report; (d) it has no 'why is OBJ not built' explanation chain; (e) it works through SuperC with a heavy setup, and one invocation covers one architecture; (f) it does not target BusyBox, Barebox, U-Boot or coreboot. I did not find evidence of these last points being claimed. kfold's differentiators would have to be (c), (d) and speed or exactness at object level, validated against klocalizer on the same patches.
    quote: "Repair usually covers all lines of a patch"
    source: Synthesis of kmax PyPI/README and the krepair paper (https://arxiv.org/html/2404.17966) |  | Own analysis from the cited sources. The points about what klocalizer does not do are inferences from absence in those pages, not stated in them. | https://pypi.org/project/kmax/
    candidate_problem: What klocalizer already solves versus what remains open
