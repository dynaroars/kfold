# What Linux developers care about in building and configuring the kernel, and where build conditions help

Synthesis for the kfold authors, 2026-10-17. Basis: eleven problem dossiers (D1-D11), each checked by an evidence auditor, a hostile competitor analyst and a fit/experiment designer, plus follow-up claims on the Kmax suite, other tools, bisection and PL prior art. Where a verifier contradicts a dive, this report follows the verifier. Appendix A lists those overrides.

Method limits that apply to every statement below:
- The shared web-search budget ran out early in almost all dossiers. Claims of the form "no tool / no request found" are weak absence evidence, not findings.
- lore.kernel.org was unreachable (HTTP 403). Everything from mailing lists comes from mirrors (lkml.iu.edu, lkml.rescloud.iu.edu, mail-archive.com, patchew, ratatoskr). Mirror coverage is partial and a summarizing fetch tool sat between us and many pages. Section 7 states what that implies.
- Numbers marked "own data" come from the repo's result files (results/agreement, results/devtasks, results/kmax) read by individual verifiers, not independently replicated.

## 1. Executive summary

1. Ranking by (evidence weight x fit with what kfold computes): D1 compile-test/coverage burden, D9 CVE applicability, D2 config for a patch, D4 blind spots, D10 reverse lookup and "why", D11 test and fuzzer configs; then D5 dead objects, D8 distro configs, D6 CI-matrix skipping, D7 condition diff, D3 stable-breakage (limitation only).
2. The strongest evidence is policy and operator artifacts, not anecdote: submit checklist, netdev and KVM profiles (build under hand-picked configs), the kernel CNA rule that CVE applicability is "up to the user", EU CRA dates (Article 14 from 2026-09-11, general application 2027-12-11), the CIP/Siemens triage tool, and the syzbot ci LLM step that guesses CONFIG_ options. About 6 independent tool groups work on D9; about 8-10 independent LKML threads on D1/D4 (all anecdotes).
3. The only gap statistics (krepair: defconfig 21.7%, one randconfig 29.2%, allyesconfig 88.5%, krepair 98.5% mean patch-line coverage, 507 patches) come from one research group that also built the competing tool, are line-level, include #ifdef arms, and say allyesconfig covers "the large majority" of code. No object-level figure exists in the literature. Our own data: 289 of 402 stable commits touch at least one object that x86-64 defconfig does not build; 3,209 of 32,877 objects (9.8%) are built by none of three x86 configs (to be re-derived, see D4).
4. Every problem except D3 is partly solved by prior art: klocalizer/krepair/koverage (config repair and patch coverage, with --view-kbuild and --show-unsat-core), Kmax per-file conditions, CIP kernel-cve-triage (file-compiled verdict plus VEX), cvehound, PatchLens, checkkconfigsymbols, JMake, undertaker/Vampyr. kfold cannot claim a new capability, only quality, validation and form.
5. Differentiators that the evidence supports: object-level exactness measured against real builds (own data: 100% precision and recall within universe on four Linux configs, 400 `why` verdicts correct; saved Kmax run scores 88.6% precision / 61.2% recall on the Debian config), a per-.config failing-conjunct verdict (documentation of the Kmax suite shows none), a whole-tree single pass (about 58 s and 212 MB for Linux 7.2.8, own data), multi-file olddefconfig-verified config-for. Not supported: "faster than krepair per patch", "no Java/SuperC", "no explanation facility exists", "first".
6. Demand for a tool is thin. The only direct request found is one anonymous LWN comment (2026-03-06). No developer survey since Hubaux 2012 and KernelCI 2020 covers it. Some reviewers refuse compile-only evidence, and the main stated pains of operators (Linaro, KernelCI) are latency and per-patch testing.
7. Out of scope for kfold: Kconfig specification bugs (kismet, Kconfirm, ConfigFix territory), #ifdef arms and header-only fixes, toolchain gates, runtime reachability, and the causes of stable build breakage (missing prerequisites, toolchain).
8. RQ3 recommendation: keep `why`, `config-for`, `blindspots`; add one new task, "triage a fix commit against a .config" (D9, soundness of the not-built verdict); run D5, D6, D8 and D11 as variants of the same harness (partition table, skip table, Debian base, syzbot base); optional bisect/skip table. Details in section 6.
9. Bottom line: pitch kfold as an exact, explainable, validated object-level oracle whose accuracy is measured against real builds and compared head-to-head with Kmax on the same objects. Do not pitch it as a solution to a felt, surveyed need.
10. Evidence gaps that matter most: no klocalizer/Kmax head-to-head has been run; Intel 0-day's per-patch config choice is undocumented; 18 of 402 unsolved commits are not broken down by architecture; the config_for compile verification covers a 40-commit sample in the file read by one verifier, versus 384 in the task statement (reconcile before publishing).

## 3. Per-problem sections (top 6)

### 3.1 D1: patches whose objects no config builds

**Statement.** A patch touches files whose build depends on a Boolean condition over CONFIG_* options and on the architecture. The documented answer is a canned set (allnoconfig, allmodconfig, sometimes allyesconfig) plus the submitter's judgement of "applicable" options. Nothing says, per touched object, whether those configs compile it or what the smallest extra change is.

**Evidence.**
- Submit checklist, https://docs.kernel.org/process/submit-checklist.html (fetched 2026-10-17): "with applicable or modified CONFIG options =y, =m, and =n." and "This is very hard to get right with testing---brainpower pays off here." The checklist does not mention COMPILE_TEST or randconfig.
- Netdev profile, https://docs.kernel.org/process/maintainer-netdev.html: "At the very minimum your changes must survive an `allyesconfig` and an `allmodconfig` build with `W=1` set without new warnings or failures." The NIPA README (https://github.com/linux-netdev/nipa) describes two allmodconfig-based build checks (one 32-bit); skipping is manual.
- KVM x86 profile, https://docs.kernel.org/process/maintainer-kvm-x86.html: "Building every possible combination of Kconfigs isn't feasible, but the more the merrier."
- Torvalds, https://lkml.iu.edu/2502.3/06618.html (2025-02-26): "my build testing is *very* limited in the configuration sense". Context: he builds allmodconfig on x86-64, "likely to be the config that compiles the most code", so this is not a complaint for a tool.
- krepair, https://arxiv.org/html/2404.17966v1 (2024-04-27): "These configurations provide no assurance that code in new patches gets compiled before testing." 507 patches sampled from about 71,000 in one year; mean line coverage defconfig 21.7%, one randconfig 29.2%, allyesconfig 88.5%, krepair 98.5%. Caveats from the auditor: x86 defconfig baseline over a sample that includes the 11% non-x86 patches; counts lines in preprocessed .i files including #ifdef arms; allmodconfig was not measured; one research group that also built the competing tool.
- Maintainers patch gaps by hand: Golaszewski, https://lkml.rescloud.iu.edu/2504.1/01019.html (2025-04-08), "There are some drivers that aren't build with allmodconfig that don't have any requirements on arch/ headers"; Kitt/rt1016, https://patchew.org/linux/20220405171158.2168762-1-steve@sk2.org/ (2022-04-05), "The rt1016 driver wasn't listed in Kconfig and Makefile, which AFAICT means it isn't ever built."; Kozlowski, https://lkml.iu.edu/hypermail/linux/kernel/2204.1/07260.html (2022-04-13), "You can still test 8-12 popular ones on a regular Ubuntu machine"; Airoha author, https://lkml.iu.edu/hypermail/linux/kernel/2502.1/00947.html (2025-02-09), "I did not succeed with that and only got into kernel configurations that broke the compilation in non trivial ways." (Greg KH first said COMPILE_TEST should be kept.); Octeon, https://lkml.rescloud.iu.edu/2306.2/07959.html (2023-06), Roeck: "CONFIG_CAVIUM_OCTEON_SOC is a choice option,". Masney (pic32), https://lkml.iu.edu/2602.3/00397.html (2026-02-23): "the issue could have been caught with a simple compile test."
- Only direct statement of the need found: an LWN comment, https://lwn.net/Articles/1061840/ (2026-03-06, anonymous commenter): "KConfig does not make it easy to get from a .c or a .diff to a list of KConfig symbols". Weakest authority; do not lead with it.
- Counter-evidence: Khan (a reviewer, not a maintainer), https://lkml.iu.edu/2603.3/01784.html (2026-03-24), "Compile testing isn't sufficient." Concerns hardware testing of a staging patch. Lunn (netdev), https://lkml.iu.edu/hypermail/linux/kernel/2604.0/01820.html (2026-04-01), "The flip side to this is that we get a lot of patches which are compile tested only." Also about hardware.

**Existing solutions and limits.** klocalizer --repair/--include and koverage (line level, SuperC, one architecture per run, "some lines may still be omitted", header-only patches unsupported, about 2% in krepair's sample but about 8.8% in the 2022 slides, different denominators). JMake (Lawall and Muller, DSN 2017, https://inria.hal.science/hal-01555711v1) is mutation-based, found allyesconfig with the right architecture sufficient for most commits, and is the direct janitor-workflow ancestor; krepair's related work says it "tries only a fixed set of standard configurations". Vampyr/undertaker (block level, reported unmaintained, supports to about Linux 3.2). Bots: 0-day reports show only "configs tested: 27 / configs skipped: 48" (https://lkml.iu.edu/2603.0/05564.html, 2026-03), never a per-object statement.

**Honest remaining gap.** (1) No published object-level measurement of what allmodconfig or the standard trio leaves unbuilt for a real commit population. (2) No explained, per-object, pre-posting answer with a verified minimal fix. (3) Demand for such a tool is not shown, only the burden.

**What kfold contributes.** An object-level lookup against a whole-tree condition table; `why` naming the failing conjunct; `config-for` with olddefconfig verification (384 of 402 .c/.S commits of v7.2.7..v7.2.8 get a configuration; 289 need a non-empty fragment, median 2 options, max 26; 18 fail, about 7 of them excluded platform drivers and about 11 unmapped incl. non-x86 arch files). Not line coverage, not #ifdef.

**Experiment (E-gap).** On the 402 commits, classify every touched object as built by x86-64 allmodconfig / by defconfig, Debian or tinyconfig only / by none, using the four real inventories (ground truth, no kfold needed). Split "none" with kfold and K into buildable on x86 by some other config (the claim) and not buildable on x86 (arch-locked, report separately). Report the share of commits with at least one unbuilt object under allmodconfig, under the union, and with none built, by directory. Add predicted allyesconfig (Kconfig-only `make allyesconfig`, no build) and predicted 32-bit allmodconfig, labelled unvalidated. Baseline for strength: allyesconfig plus `make file.o`. Falsify the motivation if the residual after dropping non-x86 objects is under about 3% of commits. Claim only "canned configs leave this much unbuilt", never "x% of patches are untested".

### 3.2 D9: is the file touched by this fix built in my configuration

**Statement.** The kernel CNA assigns CVEs to almost every bug fix and leaves applicability to the user. A downstream operator with a fix-commit list and one .config must decide per CVE whether any touched file is compiled; if none is, OpenVEX `vulnerable_code_not_present` applies.

**Evidence.**
- https://docs.kernel.org/process/cve.html: "the applicability of any specific CVE is up to the user of Linux to determine, it is not up to the CVE assignment team."
- Kroah-Hartman, https://lkml.iu.edu/hypermail/linux/kernel/2407.3/06160.html (2024-07-30): "We do not know people's use case, and can not \"gate\" CVE ids based on difference config options like this." (The page cited in the dive, 08754, is Sterba's reply.)
- EU CRA text, https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32024R2847: "This Regulation shall apply from 11 December 2027." Article 14 applies from 2026-09-11. Commission guidance C(2026) 5252 says a reported vulnerability is not necessarily applicable to the product but gives no method (paragraph 235, text-extracted by one agent).
- Siemens/CIP slides, https://opensource.siemens.com/events/2025/slides/Christoph_Steiger__Triaging_CVEs_for_the_Linux_Kernel.pdf (2025-06-04): "For CIP kernels /w CIP defconfig 90% - 95% of CVEs reported in 2024 were deemed \"not relevant\"". This is the tool authors' own claim for one config and combines commit/version checks with file-compiled checks. Do not quote it as the benefit of config analysis. The slides show per-object `built:false` with `"config": "CONFIG_MTD_NAND_ATMEL && CONFIG_MTD"` and a VEX entry; goals "Be fast" and "No false negatives".
- kernel-cve-triage README (https://gitlab.com/cip-project/cip-kernel/kernel-cve-triage/-/raw/main/README.md): "Filtered 2658/2953 - 90.01%". Per-check [successes, runs]: introduced_by_file_compiled [276, 1028], fixed_by_file_compiled [98, 393]. The checks short-circuit in sequence, so the 374 (14.1% of those filtered) is order-dependent and not a measure of config analysis; each file check removes about a quarter of the CVEs that reach it. Kernel and config of that run are not stated.
- Other demand voices (all independent of Siemens): Garmin, https://lpc.events/event/19/contributions/2020/ (2025-12-11), "discarding vulnerabilities that do not match compiled source code, or even build time configured features"; sigma-star (2024-03-13), https://www.sigma-star.at/blog/2024/03/linux-kernel-cna/ (check whether patched files are in your build via compile_commands.json); Chainguard advisory CVE-2026-53308, https://images.chainguard.dev/security/CGA-wffj-qqv4-xpvx, "is not enabled in any Chainguard kernel configuration".
- Counter-evidence on scope: Lynx, https://www.lynx.com/blog/copy-fail-dirty-frag-embedded-linux-device-risk (2026-05-26): config, built-in/module status, loaded modules, runtime availability all matter.

**Existing solutions and limits.**
- kernel-cve-triage (Kmax-based, Apache-2.0, repo created 2024-07-11): runs kmaxall once per revision and kreader per object, evaluates the formula as a Boolean over enabled CONFIG names; returns the expression; no Kconfig model; formula generation 5-10 min (author, CIP IRC 2024-08-22, https://ircbot.wl.linuxfoundation.org/meetings/cip/2024/08/cip.2024-08-22-13.02.log.txt); accuracy "only checked three kernel versions". By code reading it expands changed headers to including .o files (depth limit, falls back to relevant) and passes all arch/ directories to kmaxall, so it is stronger than kfold on headers and non-x86. Fail-open path: the auditor read the raw source and found that a kreader failure stores built=None, which the final check does not count, so a file can end as "no file is compiled" (checks/introduced_by.py lines 162-178). Read, not executed.
- cvehound (https://github.com/evdenis/cvehound, 138 stars): line-based Kbuild parser, "ifdefs are not checked", unknown files counted as affected, no accuracy numbers.
- PatchLens (FSE 2026, https://arxiv.org/abs/2606.25863): per-patch Boolean impact conditions with #ifdef, Kbuild upward walk, y and m coerced to true, 88.67% of 1,192 Linux patches resolved, about 47 ms each; its own listing shows a missed root Kbuild guard (CONFIG_NET); the 5.4% over-approximate rate is across Linux, FFmpeg and PHP; no header modelling.
- sbom-cve-check with Yocto SPDX_INCLUDE_COMPILED_SOURCES (https://github.com/bootlin/sbom-cve-check, 58 stars): exact for the built config, but needs a debug-info build and cannot answer for unbuilt configs.
- KCVEPruner: needs a finished build tree, work in progress, 3 stars.

**Honest remaining gap.** No independent false-negative measurement of any "touched file built under this .config" check against real builds exists (CIP: three versions informally; PatchLens: cross-checked against Kmax only). No tool prints which conjunct fails against a given .config in one command. Non-Linux Kbuild trees have no CVE-applicability tool that we found. Headers, #ifdef, cross-architecture, modules and runtime state are outside any file-level tool.

**What kfold contributes.** A measured soundness and agreement study of the file-built verdict with an explanation chain, from one precomputed table, for any .config.

**Experiment (E-triage).** Level A: for each of the four configs and every object in the x86 entry, compare kfold's `why` verdict to presence in the real inventory (composite parent or .ko counts as built; host programs and scripts excluded). The safety-critical metric is false "not built" (target 0). Level B: for the 402 commits, a commit is not-affected only if every touched object is not built; split x86-reachable, non-x86 arch/ files and header-only commits into separate buckets. Baselines on the same objects: Kmax kreader formulas evaluated as kernel-cve-triage does (saved run or one announced kmaxall run), cvehound's parser if callable, always-relevant. Classify every disagreement (composite objects, shell-generated names, arch mismatch, tristate, stale inventory) and test the kreader-error path. Time the table against kmaxall on one machine. Call the 402 stable commits a "CVE-like fix population", never "CVEs". Falsifiers: any systematic false not-built attributable to kfold; no better than Kmax; drops dominated by non-x86 files.

### 3.3 D2: a .config that builds a file or patch with minimal change

**Statement.** Given a base config and a target (object, file, patch), return a config that builds every target object, differs from the base in few options, and survives `make olddefconfig`.

**Evidence.**
- Tartler et al., PLOS 2011, https://sigops.org/s/conferences/sosp/2011/workshops/plos/02-tartler.pdf: "a sometimes difficult, but always tedious and error-prone task"; allyesconfig reaches 78.49% of selectable #ifdef blocks on Linux 2.6.35 x86 versus 94.40% for undertaker; Kconfig "in some cases silently overwrites user choices instead of signaling incompatible item selections".
- krepair: a single config for 97% of patches, five or fewer for over 99%, 23 in the worst case; fewer than 1.53% of defconfig options changed for 99% of patches (median 0.27%); allyesconfig build about four hours versus about 20 minutes (cite the paper, not the 3 h slide). The ICSE 2025 syzbot setting changed a median 76 options (max 1264) and disabled FS_VERITY in a case study: repair is not minimal (z3 cores "not guaranteed" minimal).
- External user, kmax issue #308, https://github.com/paulgazz/kmax/issues/308 (2026-08-16): arch-specific drivers/block/ps3disk.o reported satisfiable on x86_64; the reporter uses Kmax to generate minimized configs for testing patches. Cite by number only (double blind).
- Yamada 2020, https://lkml.rescloud.iu.edu/hypermail/linux/kernel/2003.3/08451.html: "The necessary CONFIG dependency must be met."
- Counter: KernelCI 2020 survey (https://kernelci.org/?p=109): top need is "testing individual patches sent on mailing lists", nothing on build configuration.

**Existing solutions and limits.** klocalizer --repair/--include/--include-mutex, kmax 4.10 (released 2026-08-18). Verified limits from docs and code: formulas "may not be exact" (docs/advanced.md); "Passing multiple architectures is not supported."; composite units not built directly; CONFIG_BROKEN stops the search; Boolean model (the CLI passes --disable-tristate-support to kclause; --modules is a post-hoc rewrite of on-options to m; PR #304 of 2026-01-16 reverted to a Boolean model, issue #230 open); no per-.config explanation; no accuracy study of the Kbuild constraints (Kmax 2017 validated only the file set: 0 missed of 20,804 files in v3.19, 633 in BusyBox). Setup: pipx, apt packages, plus Java/SuperC only when line constraints are used (code reading, not run). Open install issues: #272 (GCC 14 on Arch needs CC=gcc-13), #313 (Python 3.11+ 'rU' mode, may not be hit by the kmax CLI). Bundled Kconfig parsers go up to v7.1; Linux 7.2.8 is unverified.

**Remaining gap.** Exactness measured against builds, per-.config explanation, a verified patch-level multi-file result, and a minimality measurement on the same commits. Header-only, #ifdef and non-x86 patches stay out.

**What kfold contributes.** `config-for` over a whole-tree table (own data: 384 of 402 solved, median 2 options in 289 non-empty cases, base defconfig). The comparison with krepair's 1.53%/median 76 is a different sample, base and granularity and must stay descriptive.

**Experiment (E-cfg).** Re-run config-for on the 402 commits with three bases (defconfig, Debian, syzbot ci config, see D11). Report solved rate, options changed (absolute count and percent under a stated definition), olddefconfig retention, compile success (reconcile whether the existing compile check covers all 384 or a 40-commit sample), and the 18 failures by cause with non-x86 broken out. Baselines: allyesconfig plus `make file.o` (predicted from Kconfig only), the naive leaf-symbol rule. Optional, needs user approval and strictly one process at a time: klocalizer on about 30 commits (smoke test on one first), comparing config size, runtime, failures. Pre-register falsifiers: the strong baseline succeeds on essentially all objects config-for solves; klocalizer equals kfold on verdicts and size.

### 3.4 D4: blind spots, objects no standard or CI config builds

**Statement.** Given a tree and a user-supplied set of configs, which objects have a condition no config satisfies, why (failing conjunct) and which MAINTAINERS entry owns them.

**Evidence.**
- Hovold, https://lkml.iu.edu/2511.2/04659.html (2025-11-22, Koul's reply quoting the patch): "There seems to be nothing preventing the driver from being compile tested so enable that for wider build coverage." Same author, tegra IOMMU https://lkml.iu.edu/2510.3/03324.html and k3-socinfo https://lkml.iu.edu/hypermail/linux/kernel/2601.1/11851.html ("enable that by adding the missing input prompt"). Count Hovold as one source.
- Golaszewski (D1 above); Kitt rt1016 (D1 above).
- Torvalds via LWN, https://lwn.net/Articles/1050027/ (2025-12-12): "some repositories clearly are not seeing any testing at all." The allmodconfig "can thus hide problems" line is Corbet's wording, not a Torvalds quote.
- U-Boot: Glass, https://www.mail-archive.com/u-boot@lists.denx.de/msg98954.html (2012-11-07), "can we easily find code that is not enabled by any existing board?" (a question, not a request for a tool); Wood, https://www.mail-archive.com/u-boot@lists.denx.de/msg216666.html (2016-06-19), "there is no board that enables this code in order to get build coverage"; Rini, https://www.mail-archive.com/u-boot@lists.denx.de/msg436281.html (2022-03-31), "This driver is not enabled by any board and not converted to DM_ETH." (method of discovery not stated). buildman lists "checking commits for changed files and building only boards which use those files" as an idea (https://docs.u-boot-project.org/en/latest/build/buildman.html).
- barebox, https://www.mail-archive.com/barebox@lists.infradead.org/msg52399.html (2025-03-26): "Building allyesconfig in CI allows us to catch early compile-time breakage when changes are done treewide."
- Counter-numbers: krepair allyesconfig 88.5% mean patch coverage; Hovold's own commit text says COMPILE_TEST should not enable every driver "we have \"allyesconfig\" for that" (about the COMPILE_TEST default, https://patchew.org/linux/20250725075429.10056-1-johan@kernel.org); Torvalds: build failures in his merge window are rare.
- Independent sources: 6-8, not the 25 items listed. Many anecdotes are ARCH-gated drivers that other architectures' configs do build.

**Existing solutions.** COMPILE_TEST by hand; allmodconfig/allyesconfig; 0-day randconfig sampling (63% of 36,115 reports in krepair's study); Bergmann's private randconfig loop (https://speakerdeck.com/ennael/large-scale-kernel-build-testing-on-a-desktop, 2026-09-28, no coverage measure); Kmax koverage (patch coverage, build-based) and kreader (per-object condition), so a blindspot loop is a short script over existing outputs; kmax issue #138 (open) asks for a dump of compiled files.

**Remaining gap.** Effect size: objects reachable on x86 under the Kconfig model that the usual configs still miss. Whether maintainers want the report. How much is intentional (arch, hardware, BROKEN, staging).

**What kfold contributes.** A per-object report over a config set with the failing conjunct and MAINTAINERS grouping, from an exact denominator (all objects), runnable on U-Boot, barebox, coreboot, BusyBox.

**Experiment (E-blind).** Own data: 3,209 of 32,877 objects built by none of allmodconfig, allyesconfig, defconfig (510 MAINTAINERS entries; 349 non-x86 arch symbol, 2,196 "not enabled by any provided config", 664 no single pivot). Treat as "not built by three x86 configs", not "never built"; the list contains composite/intermediate artifacts (crypto/crypto.o, .tmp_vmlinux1.btf.o style) that must be filtered. Re-run with Debian added. Partition: (a) arch-gated, (b) unreachable on x86 under K, (c) reachable under K but missed by the matrix (actionable). Stage 1: false-blind rate against the real inventories (target about 0). Stage 2: 40 stratified class-(c) objects, config-for, olddefconfig, compile; manual triage (BROKEN, staging, hardware-only, neglect). Stage 3 baselines: 50 randconfig `.config` files generated one at a time and evaluated with kfold (no builds) to plot cumulative class-(c) coverage; the Kmax-formula script on the same configs with Jaccard overlap, every disagreement adjudicated against inventories. Falsifiers: false-blind above 1%, fewer than half of class (c) with a verified witness, class (c) negligible, randconfig sampling covers nearly all of it.

### 3.5 D10: reverse lookup and explanation

**Statement.** (A) Which Makefile condition builds X and which conjunct fails in this .config. (B) Why the guarding option cannot be turned on or was dropped. kfold answers (A) exactly and (B) only through K.

**Evidence.**
- 2006, https://lkml.iu.edu/hypermail/linux/kernel/0603.0/0862.html: manual answer "obj-$(CONFIG_8139TOO) += 8139too.o" (Engelhardt).
- Arch forum 2013, https://bbs.archlinux.org/viewtopic.php?id=158476: "I just can't find them anywhere." Twelve replies, none mentioning a Makefile.
- Linux Magazine 244 (2021), https://www.linux-magazine.com/Issues/2021/244/Kconfig-Deep-Dive: "I looked through the requisite driver makefiles to determine which `CONFIG` options needed to be enabled." and, for the Kconfig half, "the kernel gave no indication as to why the specific `CONFIG` option was ignored".
- ConfigFix, https://arxiv.org/pdf/2012.15342: "Xconfig does not even show which parts of the constraint are unmet." Hubaux et al., https://gsd.uwaterloo.ca/sites/default/files/vamos12-survey.pdf (VaMoS 2012): 20% of 81 usable answers (97 respondents) need at least a few dozen minutes to activate an inactive option. 2012, mostly non-developers, Kconfig half.
- Airoha and Octeon threads (D1). Attribution fix: "not worth the effort" in the Octeon thread is Herring's; Le Moal's reason is the rc7 timing.
- Counter: LWN 2025, https://lwn.net/Articles/1026337/: configuration is the main obstacle, but the pain is Kconfig-side.

**Existing solutions.** menuconfig symbol search (needs symbol names); kernelconfig.io (dependencies, selects, source files per version, https://www.kernelconfig.io/about.html); kmax `--view-kbuild` (static Kbuild constraint of a unit and its parent directories, e.g. `[And(CONFIG_SQUASHFS, CONFIG_SQUASHFS_DECOMP_MULTI)]`; it ignores any .config), `--show-unsat-core` (constraints blocking a forward request; no sample output documented), `--report-all`; the --approximate path drops soft .config assumptions and logs only counts; koverage FILE_EXCLUDED has no cause; CIP code returns the evaluated expression. localmodconfig regexes simple obj-$(CONFIG_X) lines. Yocto configcheck names dropped options without the cause.

**Remaining gap.** A single command that evaluates the condition against a given .config and prints the failing conjuncts, with an accuracy figure against builds. The Kconfig half remains, where klocalizer's unsat core over Kbuild plus Kconfig may be stronger than kfold's over-approximate K. Say so.

**What kfold contributes.** `why` (own data: 400 of 400 verdicts correct across four Linux configs; directory-route gates account for 18-39 of 50 unbuilt cases per config, where grepping one Makefile line is wrong; pivotal_symbols is empty for 9-31 of 50 unbuilt objects, so a single flip is insufficient there), plus a Z3-minimal suggested change.

**Experiment (E-why).** Counterfactual sufficiency. For 100 absent objects per config (allmodconfig primary; stratified by failing kind), apply `why`'s suggested change, run olddefconfig, record retained options, compile the single object, one process at a time (about 10 s each in the existing harness; run a pilot of 10 and tell the user the total before the full run). Classes: (a) suggestion works, (b) blocked on the Kconfig side (options dropped or K unsat), (c) options retained but object missing (kfold error or non-Kbuild gate), (d) verdict disagrees with inventory. Baselines: B1 nearest-Makefile-line symbol, B2 Kmax formula symbols from the saved run, B3 `why` without K. Hand-check 50 class-(b) reasons and label them a limitation. Falsifiers: sufficiency within a few points of B1 on directory-route strata; (c)+(d) above 10%; the named blocker wrong in more than about 20% of the hand check.

### 3.6 D11: test and fuzzer configurations (KUnit, syzbot)

**Statement.** A dynamic test exercises code only if the config compiles the object under test. The object-to-config step is done by hand or by heuristic and nothing re-verifies it.

**Evidence.**
- syzbot ci prompt, https://raw.githubusercontent.com/google/syzkaller/master/pkg/aflow/flow/fuzzing/patch_triage.go (workflow added 2026-06-02, config step 2026-06-09, name validation 2026-06-19): "Identify any specific CONFIG_ options required to properly compile and reach the modified code:". Validation only checks that the names exist in Kconfig. A moving target; cite a commit.
- All nine production targets use one config, https://raw.githubusercontent.com/google/syzkaller/master/syz-cluster/overlays/gke/prod/global-config.yaml: "kernel_config: upstream-apparmor-kasan.config". The build step sets each EnableConfigs entry to y, converts =m to =y, and checks nothing afterwards (syz-cluster/workflow/build/main.go; build.Image internals not opened). The fuzz step skips fuzzing when base and patched symbol hashes are equal, and treats an unreached patched area as fine ("We did not reach the modified parts of the kernel, but that's fine."); it appears to build both kernels anyway (differential fuzzing), so a static check saves the fuzzing run and the choice of options, not necessarily a build.
- ICSE 2025, https://www.paulgazzillo.com/papers/icse25.pdf (Hasanov, Nagy, Gazzillo): syz-kconf covers 43.2% of patched lines (kAFL 24.1%, defconfig 21.8%), krepair raises it to 98.6%; fuzzing found 35 bugs versus 13. This corrects the dive's "42% is not in the paper".
- KUnit: all_tests.config "is manually maintained" (header, 40 CONFIG_ lines, UML). Fix commits: 4ea404fdbc39 (Brown, 2025-04-22; select removed from PRIME_NUMBERS, tests "neither built nor run"; not re-verified verbatim), cefd81e76a8c (Gunthorpe, 2026-01; GENERIC_PT made unselectable; kunit_tool error "Not all Kconfig options selected in kunitconfig were in the generated .config."), 34b5c0132952 (Golaszewski, 2026-06-29; one added line GPIOLIB). The DAMON fix (2024-03) is a Kconfig rename and its quoted phrase is not in the commit. KUnit docs (https://docs.kernel.org/dev-tools/kunit/running_tips.html): "tests could theoretically depend on incompatible options, so handling that would be tricky."
- Adjacent: FCC, https://arxiv.org/abs/2608.15225: LLM plus olddefconfig feedback, "critical options may be silently rolled back during make olddefconfig".

**Existing solutions.** klocalizer applied to syzbot configs (ICSE 2025; no adoption by syzbot found: zero hits for klocalizer/krepair/kmax in google/syzkaller issues and PRs and in torvalds/linux commits); kunit_tool validate_config (detects, does not repair); a symbol-level check (list *_KUNIT_TEST symbols unset after olddefconfig of all_tests.config) catches the PRIME_NUMBERS case with no Kbuild analysis.

**Remaining gap.** An object-level, olddefconfig-verified, explained answer to "are the patched or test objects in this config" before building; the measured miss rate of the LLM step is unknown.

**What kfold contributes.** The Kbuild half as a deterministic oracle: sound negative (object not built), failing conjunct, minimal verified change on top of the syzbot config.

**Experiment (E-fuzz).** Fetch upstream-apparmor-kasan.config (pin the commit hash), apply the =m to =y rewrite, run olddefconfig on 7.2.8 x86_64, run `why` for the touched objects of the 402 commits, report fully/partly/not built, the blocking-conjunct histogram by MAINTAINERS entry, config-for options changed on the syzbot base, a 20-object single-object compile spot check (no build exists for that config), and the retrospective check on the three verified KUnit fix commits against the symbol-level baseline (n=3, an anecdote). The LLM overlay cannot be reproduced; say so. Falsifiers: any systematic false not-built (above about 2%); under about 5% of commits touch unbuilt objects; config-for verification clearly worse than on defconfig.

## 4. Competitor analysis

### 4.1 The Kmax suite (klocalizer, krepair, koverage, kreader, kismet)

Verified facts. Repo is github.com/paulgazz/kmax (the other two URLs 404); kmax 4.10 released 2026-08-18; 72 stars, 29 forks, 0 dependent repositories, about 330 PyPI downloads in the last month (mirrors not excluded). The `kmax` Kbuild evaluator is pure Python (pymake plus z3); `kmaxall` is sequential. klocalizer instantiates SuperC only when a line constraint is given (code reading, not run). Docs and code disagree on kmaxall (advanced.md still shows a removed -g option, issue #284). Install: pipx plus apt packages; no Python, Java, RAM or disk figure documented. Non-Linux: BusyBox by manual workflow (issue #249 closed, #11 open for other Kconfig filenames); issue #236 says klocalizer and kismet are "setup for Linux" and coreboot needs a script for wildcard paths; no mention of U-Boot or barebox found. The 2017 paper claims BusyBox, coreboot, uClibc, EmbToolkit as targets but evaluated only Linux v3.19 and BusyBox v1.25.0.

Integration claims. LWN (https://lwn.net/Articles/1034811/, 2025-09-10): "It has been integrated into the Intel 0-day test suite". The kmax repo's own bugs_found.md says only kismet was added (first reports May 2022). Do not write that 0-day uses klocalizer. Adoption evidence: CIP kernel-cve-triage (Kmax formulas), one issue-tracker CI user (#308), a UCF thesis (KBootRepair). The 0-day config choice per patch is undocumented (lkp-tests README is silent; 0-day reports show fixed per-arch libraries plus randconfig, "configs tested: 19" in Feb 2025, 12 tested/119 skipped in Sept 2025).

Timing, kept apart: Kmax 2017: 77.52 s mean per architecture on v3.19 (84.15 s x86; 4.2 GHz 4-core, 16 GB). krepair: kclause 2-3 min, kmax 10-15 min whole-tree; with per-file on-demand collection and caching, maximum about 19 min and under one minute for 93.8% of runs (EPYC 7742, 512 GB). ICSE 2025: configuration time median 44.27 s, max 172.99 s. Our saved Kmax run on Linux: 6,275 s and 28.5 GB RSS with arguments `-T -DSRCARCH=x86 Kbuild lib` (tristate on, a different invocation than the 2017 figure); kfold: 57.96 s and 212 MB in results/agreement/linux.full.json, but 138.7 s median in STATUS.md. Reconcile the two kfold figures and rerun Kmax in the default invocation on the same machine before any speed claim.

### 4.3 CVE-applicability tools

See D9 section. kernel-cve-triage is the closest: same verdict, VEX output, production use at CIP, header expansion and multi-arch input that kfold lacks, flat expression without a per-conjunct failure report, per-revision Kmax cost, a possible fail-open path. cvehound and PatchLens bound any claim that nobody derives Kbuild conditions from Makefiles. sbom-cve-check is exact but needs a build. All of them stop at the file or hunk; none models runtime.

### 4.4 Claims the paper must avoid

- "First", "novel capability", "no tool exists" (write "not documented in the tools we examined").
- Line-level, #ifdef or header coverage; "patch coverage" for object coverage; comparing 21.7%/88.5%/98.5% with object numbers.
- Speed over krepair or Kmax without a same-machine run; "kmax takes 10-15 minutes" as the bottleneck kfold replaces.
- "klocalizer has no explanation" or "Boolean y only".
- 90-95% or 14% as the benefit of config analysis.
- "kfold would have prevented any stable breakage" (it would not have for any incident examined).
- Demand claims beyond "the burden is documented"; "nobody has tried" (ICSE 2025 and DSN 2017 did).
- "0-day uses klocalizer/krepair".
- Treating 3,209 / 9.8% as "never built".
- Treating the 402 stable commits as CVEs or as new-driver patches.

### 4.5 PL positioning (missing from the dossiers, from follow-ups)

kfold's guarded-word variables with merging at conditionals belong to the variational-execution and value-summary family, not new symbolic-execution technique: variational execution definition and its join strategy (arXiv 1809.04193), Varex (ICSE 2014), Multi-SE value summaries (Sen et al.), state merging (Kuznetsov et al., PLDI 2012), SuperC's fork/merge for C (PLDI 2012), TypeChef (OOPSLA 2011), choice calculus (TOSEM 2011), lifted vs sampling analysis (FSE 2013). Closest build-system prior art: Zhou et al. 2015 (SYMake, Select nodes, no sub-make, tested on artificial Makefiles of at most 8 options), Nguyen and Nguyen 2020 (symbolic execution of make with Z3; ran out of memory on sound/soc/codecs, drivers/mfd, and had only basic merging), Kmax 2017 (guarded sets with BDD path conditions), GOLEM (runs Make), KBuildMiner (patterns). What kfold can state: whole-tree Linux in about a minute with a measured agreement result, which these papers do not report. Not claimable: handling of integer or string options (CMake paper notes KBuild techniques handle only three-valued options; quick grep found only boolean/tristate modelling), formal Make semantics (none located).

## 5. Counter-evidence and scope limits

Out-of-scope clusters, each with an example:
- Kconfig-specification bugs and gating: kismet (ESEC/FSE 2021, 781 unmet-dependency alarms), Kconfirm (https://lkml.iu.edu/2607.3/03886.html, 1282 default-check alarms at v7.2-rc4, Kconfig-level), kconfig-sym-check (merged via kbuild-7.2-1), ConfigFix (merge status unverified), k3-socinfo (promptless option), the Octeon choice, iommupt (GENERIC_PT unselectable), PRIME_NUMBERS (select removed). kfold sees the symptom (object unbuilt), and names the cause only through the over-approximate K.
- #ifdef-level dead code and uncompiled arms: Tartler 2011 (1,778 dead of 16,444 conditional blocks), the DVB leak (syzbot memory-checking config, about three months of config-caused delay, a CPP case), #include-d KUnit tests.
- Headers: krepair about 2% of its sample, Gazzillo slides about 8.8% (1,177 of 13,411 on v5.13); both unsupported by kfold. Non-x86 about 9.7% on the slides (1,296), 11% need cross-compilation in krepair; kfold's entry is x86 and 18 of 402 commits are unsolvable there.
- Toolchain: clang-nightly, gcc-8 C99 loops in stable-rc, CC_HAS_* and cc-option gates (not examined for kfold).
- Runtime and hardware: Lynx (loaded modules, runtime availability), KCVEPruner loaded-module lattice, Khan and Lunn on hardware testing.
- Stable breakage: every incident with a visible cause is a missing prerequisite (5.15.197-rc1 arm/mips, 6.1.136-rc1 s390, 6.12.53-rc1 s390, 6.1.165), toolchain, or a header problem. "Build-fix-only releases": at least four in about 14 months (6.6.71 and 6.1.126 in Jan 2025, 6.1.137 in May 2025, the Mar 2026 triple), a lower bound from non-exhaustive search. The (arch, config) pair is the detection surface, not the fault; the -rc process drops offending patches ("dropped.").

Evidence against the demand story:
- krepair's own data say allyesconfig averages 88.5% of patch lines; a per-patch cover is easy (97% need one config).
- Torvalds and Roeck rely on allmodconfig plus bots; linux-next catches hard build breaks.
- KernelCI 2020 survey (just under 100 responses): top need is per-patch testing; Linaro (LKFT, 2024: about 430k builds, 271 LTS releases) names fragmented CI and slow feedback, answered by scale-out.
- Some operators already have workable heuristics (syzbot ci LLM step, OpenWrt install-time checks, Ubuntu module-check until 2024).
- Kbuild is "odd fixes" and Kconfig unmaintained since Yamada stepped down (LWN 1032722, 2025-08-06): maintainers are unlikely to adopt tooling soon.
- Demand evidence is dominated by COMPILE_TEST coverage threads, which concern D4 more than D6 skipping.

## 6. Concrete recommendation for RQ3

### 6.1 Tasks to keep, in priority order

0. Prerequisite for everything: object-level accuracy against the four real inventories (done, 100% within universe), the 400 `why` verdicts, and the Kmax same-object comparison. Every task below reuses it; do not repeat it as a "task".
1. **Triage a fix commit against a .config (D9, new).** Cheapest, strongest sense of purpose, independent demand. Evaluate as in E-triage. Priority 1 because it gives the sharpest falsifiable number (false not-built = 0) and a head-to-head with the CIP method. Effort 4-6 person-days; minutes of compute.
2. **config-for (D2, with D11 and D8 variants).** Keep and extend: three bases (defconfig, Debian, syzbot), options-changed distribution, failure taxonomy, naive and allyesconfig baselines, worked examples from Debian #1126062 (DLN2) and #1112317 (GPIB; the GPIB request got partial maintainer action, DLN2 is still not set). About 5-6 person-days; klocalizer on 30 commits is optional and needs approval (install on this Arch machine has known friction: #272, #313, parser v7.1).
3. **blindspots (D4, with D5 and D6 sub-tables).** Re-derive with Debian added and artifact filter; partition (a)/(b)/(c); inside (b) split undefined-symbol / unsat / BROKEN as D5 requires (soundness needs both the Makefile condition and K to over-approximate; state both); baselines checkkconfigsymbols (superset test), randconfig curve, Kmax-formula script; mutation test with about 100 planted defects for recall; replay the kconfiglint parents and the mlx90635/pidfd cases. About 7 person-days.
4. **why (D10).** Counterfactual sufficiency as in E-why. About 5 person-days.
5. **Optional, exploratory skip table (D6 plus the bisect idea).** For each commit in the 402 and each of the four configs, count commits whose touched objects are all unbuilt (skippable), by configuration. Do not infer it from the 72% figure: 289 commits have at least one unbuilt object under defconfig, not all. Sound skipping only if no touched object can be built and the commit touches no header, Kconfig, Makefile or script; fall back to the full matrix otherwise (Zephyr does). Bisect caveat: the kernel bisect guide re-runs olddefconfig per step, so the effective config can change between steps. Baselines: `git bisect start -- <paths>` (history simplification can hide merge contributions), ccache (LWN 1093398: about 960 s clean vs about 90 s fully cached), syzkaller's post-hoc NoopChange detector. No Linux-specific prior art on build-condition skipping found (search incomplete). Run only if the counts are non-trivial.
6. **D7 condition diff.** Related work plus a limitation. If space remains, run tools/diff_build_evolution.py on 7.2.7 vs 7.2.8 as a control, restricted to Makefile-level (Bin A) changes, with a textual-diff baseline; skip the Debian-changelog recall idea (mostly Kconfig-side, no object names).

Drop as tasks: D3 (limitation sentence), D8 and D11 as separate RQs.

### 6.2 Evaluation on available assets

Assets: Linux 7.2.8 whole tree; four builds with inventories (i386 tinyconfig, x86-64 defconfig, Debian, allmodconfig); BusyBox, Barebox, U-Boot, coreboot with one build each; 437 commits (402 .c/.S); saved Kmax runs on Linux and BusyBox; allyesconfig config (no inventory). Under the project rules: one process at a time, results to files, no physical builds without asking, no new Kmax or klocalizer run without announcing the expected duration (a Kmax whole-tree run is minutes to hours depending on invocation).

Cross-cutting design rules: stratify non-x86 objects and header-only commits as their own buckets; report 18 failures by cause with non-x86 broken out; fix "in scope" definitions before looking at results; report both witnessed (inventory) and K-claimed (upper) coverage; never compare line-level krepair numbers with object numbers; state the denominator (402 .c/.S commits, not 437) in every percentage; show disagreements with causes, not only percentages.

1.
