=== PROBLEM P14: Deriving test and fuzzer configs for the objects under test (KUnit, syzbot, per-patch fuzzing)
who: KUnit test authors, fuzzer operators (syzbot, syzbot ci), kernel testing MC participants
strength: Moderate to weak. About 9 claims; docs admissions (260), a talk abstract (64) and slide statistics (184, 185) from independent sources. The 42% syzbot figure is from slides via snippet (113). No developer asks for this tool.
existing: Hand-written .kunitconfig, syz-kconf with config fragments, KUNIT_ALL_TESTS, merge_config.sh.
gap: Compute the .kunitconfig or fuzzing fragment that builds a set of test objects or a patch's files, and verify it keeps them built.
fit: partial - The object-to-config step is within scope. Dynamic coverage and Kconfig dependency generation are the larger parts of the problem, and demand comes from docs more than from complaints.

--- supporting claims
[51] (pain_point/anecdote, 2022-06-22) Slides give a case where a 2016 memory-leak bug lay undetected until 2020-11 because syzbot's memory-checking config disabled the guarding option (CONFIG_MEDIA_CONTROLLER_DVB); the fuzzer found it only after its configs were regenerated and happened to include it. Slides also note syzbot's hand-crafted configs must be 'kept update with changes to defaults'.
    quote: "but CONFIG_MEDIA_CONTROLLER_DVB is disabled in its mem checking config"
    source: Krepair slides, slides 5-6 'example of bug missed due to wrong .config' | Paul Gazzillo, Necip Yildiran | Open Source Summit North America 2022 | https://paulgazzillo.com/files/oss2022.pdf
    candidate_problem: Fuzzer/CI blind spots: which objects/files are never built by any maintained config (the 'blindspots' use case).

[64] (need/anecdote, 2025-12-12) LPC 2025 Kernel Testing MC, 'syzbot ci: continuous patch series fuzzing' (Nogikh, Google): applies incoming patch series to an automatically chosen base tree and fuzzes the code paths the patch modifies; says build/boot failures stall fuzzing once landed; findings sent to more than 50 series as of Sept 2025. Targeting 'code paths modified by the patches' needs a config that actually builds the touched files.
    quote: "Many regressions, including build/boot failures and shallow bugs, can stall the broader fuzzing effort once they land."
    source: syzbot ci: continuous patch series fuzzing | Aleksandr Nogikh (Google) | Linux Plumbers Conference 2025, Kernel Testing & Dependability MC | https://lpc.events/event/19/contributions/2195/
    candidate_problem: Per-patch pre-merge testing (fuzzing and build) needs the object-to-config mapping for the touched files; syzbot ci/kci-dev are plausible consumers. Page does not itself discuss configs.

[81] (pain_point/anecdote, 2024-07) Anecdote: a Linux memory leak that syzkaller can detect stayed in the kernel for months because the config option guarding the buggy code was not enabled in syzbot's fixed config set; found only after a later default-config change. Shows fuzzers/CI have object-level blind spots that go unnoticed.
    quote: "remained in the kernel for months, because the configuration option controlling inclusion of the buggy code was not enabled"
    source: Maximizing Patch Coverage for Testing of Highly-Configurable Software without Exploding Build Times | Yildiran, Oh, Lawall, Gazzillo | FSE 2024 (section 2) | https://arxiv.org/abs/2404.17966
    candidate_problem: Code/objects never built by the CI or fuzzer configs (blindspots)

[129] (existing_tool/tool, n.d.) syzbot's configs are generated by syz-kconf from main.yml plus config fragments (bits/), chosen by instance features (arch, compiler, upstream or stable). Each instance gets a normal and a baseline config for minimization. The configs are hand-curated fuzzing configs. The FSE paper says syzbot relies on a small, fixed set of configuration files, which the slides credit with only 42% mean patch coverage. This is a fuzzing-oriented config, not a per-patch config generator.
    quote: "generated by the `syz-kconf` tool"
    source: syzkaller dashboard/config/linux README |  | GitHub (the backticked quote is the summary's wording; verify in the README) | https://github.com/google/syzkaller/blob/master/dashboard/config/linux/README.md
    candidate_problem: Fuzzer configs are fixed and not tied to the objects a patch touches

[184] (statistic/statistic, 2023-11) syzbot (Google, LPC 2023): about 17k findings detected, about 6k reported to LKML, 3,400+ kernel commits mention syzbot, 4,800+ resolved findings on the dashboard. Fuzzing runs on 25 syzkaller instances with about 150-200 VMs, only for GCE/x86_64, GCE/arm64, qemu x86_64, arm32, arm64 and RISC-V, on a handful of trees (mainline, linux-next, bpf, bpf-next). 72% of ever-addressed reports are addressed within 45 days.
    quote: "Linux kernel is fuzzed on 25 syzkaller instances using ~150-200 VMs in total."
    source: Syzbot: 7 years of continuous kernel fuzzing | Aleksandr Nogikh (Google) | Linux Plumbers Conference 2023 (slides) | https://lpc.events/event/17/contributions/1521/attachments/1272/2698/LPC%2723_%20Syzbot_%207%20years%20of%20continuous%20kernel%20fuzzing.pdf
    candidate_problem: Fuzzers only exercise code that the few fixed syzbot configs compile in; objects outside those configs get no dynamic testing.

[185] (statistic/statistic, 2023-11) syzbot patch-testing requests grow from about 300 in 2018 to about 1,000 per year in 2021 and 2022, and about 1,250 extrapolated for 2023 (values read from a bar chart). These are developers asking a CI to build and run their patch because they could not do so locally, a sign of demand for patch-level build feedback.
    quote: "Patch Testing Requests"
    source: Syzbot: 7 years of continuous kernel fuzzing | Aleksandr Nogikh (Google) | Linux Plumbers Conference 2023 (slides) | https://lpc.events/event/17/contributions/1521/attachments/1272/2698/LPC%2723_%20Syzbot_%207%20years%20of%20continuous%20kernel%20fuzzing.pdf
    candidate_problem: Developers rely on a bot to build and test patch variants; knowing the config for the touched objects speeds this up.

[259] (policy/policy, n.d.) Kunit style rules make test objects Kconfig-gated, tied to CONFIG_KUNIT and KUNIT_ALL_TESTS, with 'depends on' the feature under test, so tests are separate CONFIG-gated objects.
    quote: "Every test suite should be tied to a Kconfig entry."
    source: Test Style and Nomenclature (KUnit) |  | docs.kernel.org | https://docs.kernel.org/dev-tools/kunit/style.html
    candidate_problem: Question 'which config builds this KUnit test object' arises for each test. kfold's config-for gives the answer. The KUnit docs do not require tests to build in all configs, only the Kconfig structure.

[260] (pain_point/policy, n.d.) KUnit running tips admit that test config dependencies are an edge case that test authors rarely consider, and that merging .kunitconfig fragments across directories is unreliable because tests may depend on incompatible options.
    quote: "tests could theoretically depend on incompatible options, so handling that would be tricky."
    source: Tips For Running KUnit Tests |  | docs.kernel.org | https://docs.kernel.org/dev-tools/kunit/running_tips.html
    candidate_problem: Computing a consistent .kunitconfig for a set of test objects is an unsolved manual problem, and config-for could generate one from object conditions plus the Kconfig model.

[299] (need/tool, n.d.) KUnit documentation: the user must list the Kconfig options and their dependencies by hand in .kunitconfig. The tool only warns if options did not survive olddefconfig. No config is computed from the tests or objects. Per search-result summary, so approximate.
    quote: "the list of kconfig options required to run the desired tests, including their dependencies"
    source: KUnit Getting Started |  | docs.kernel.org | https://docs.kernel.org/6.1/dev-tools/kunit/start.html
    candidate_problem: config-for for tests: hand-written dependency lists (the page was not opened; quote taken from a search-result summary)
