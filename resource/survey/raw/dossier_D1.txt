=== PROBLEM P1: Patches never built by the author or by CI (H1)
who: Patch authors, subsystem maintainers, linux-next integrators, CI operators
strength: Strong. About 27 claims. Statistics exist (507-patch krepair study, 13,411-commit v5.13 slide data, 36,115 0-day reports). Sources are partly independent (academic measurement plus maintainer remarks on LKML/LWN), but most numbers come from one research group. Counter-weight: bots catch hard breaks after merge (193).
existing: 0-day/kernel test robot, linux-next daily builds, KernelCI, TuxSuite, syzbot patch testing; krepair/klocalizer for repair; allmodconfig on x86_64 as the Torvalds proxy.
gap: No pre-posting, per-object answer to 'is each touched object built by the configs I (or CI) used'. There is no per-object coverage report for bots. Header-only patches (about 2%) and #ifdef arms are not covered at object level.
fit: partial - The object-level question (is the touched .o built under config X, and under which configs) is exactly kfold's output. The headline statistics are line-level and include #ifdef and header cases that kfold cannot see, so object coverage will be higher than the quoted line coverage. Do not reuse the numbers as kfold's gap without re-measuring at object level.

    source: Linux Kernel patch submission checklist |  | docs.kernel.org | https://docs.kernel.org/process/submit-checklist.html
    candidate_problem: Ad hoc, random choice of configs to build-test. kfold's config-for could replace this with configs derived from the objects the patch touches.

[228] (policy/policy, n.d.) The checklist requires the 'allnoconfig' and 'allmodconfig' build targets and building out-of-tree (O=).
    quote: "Passes `allnoconfig`, `allmodconfig`" and "Builds successfully when using `O=builddir`"
    source: Linux Kernel patch submission checklist |  | docs.kernel.org | https://docs.kernel.org/process/submit-checklist.html
    candidate_problem: Whole-tree builds are the default proxy for 'my change compiles'. Object-level conditions could show which objects those proxies never build (blindspots).

[229] (policy/policy, n.d.) The checklist requires builds on multiple CPU architectures, locally or on a build farm. It names word size and endianness as the portability axes.
    quote: "Builds on multiple CPU architectures by using local cross-compile tools or some other build farm."
    source: Linux Kernel patch submission checklist |  | docs.kernel.org | https://docs.kernel.org/process/submit-checklist.html
    candidate_problem: Architecture dimension of 'did you compile this': which ARCH and config builds the touched object. This is the kind of object-to-config question kfold answers. Whether kfold handles multiple ARCHes is a limitation to check.

[232] (policy/policy, n.d.) submitting-patches requires every patch in a series to build, which is bisectability. It mentions no configurations.
    quote: "take special care to ensure that the kernel builds and runs properly after each patch in the series."
    source: Submitting patches: the essential guide to getting your code into the kernel |  | docs.kernel.org | https://docs.kernel.org/process/submitting-patches.html
    candidate_problem: Per-patch build condition checks across a series. Series-wide config-for could catch mid-series breakage.

[233] (counter_evidence/policy, n.d.) submitting-patches has no explicit rule on which Kconfigs or architectures to compile with. Its only testing language is the Tested-by tag, which says 'in some environment'. The concrete multi-config build burden lives in submit-checklist and subsystem profiles, not in the central submission guide.
    quote: "A Tested-by: tag indicates that the patch has been successfully tested (in some environment) by the person named."
    source: Submitting patches: the essential guide to getting your code into the kernel |  | docs.kernel.org | https://docs.kernel.org/process/submitting-patches.html
    candidate_problem: Compile coverage is a soft, undocumented norm in the central guide. Evidence for it has to come from subsystem profiles and the checklist.

[234] (policy/policy, n.d.) Networking (netdev) sets a hard minimum bar. Changes must pass allyesconfig and allmodconfig with W=1 and add no new warnings or failures. Authors must test locally and must not use the CI as a compile service.
    quote: "At the very minimum your changes must survive an allyesconfig and an allmodconfig build with W=1 set" ... "without new warnings or failures."
    source: Networking subsystem (netdev) |  | docs.kernel.org | https://docs.kernel.org/process/maintainer-netdev.html
    candidate_problem: The netdev bar is allyesconfig plus allmodconfig. That is a coarse proxy: objects whose condition is unsatisfiable together with those configs (mutually exclusive or non-default options) are never compiled. A blindspots analysis against exactly these two configs is the matching tool.

[235] (policy/policy, n.d.) netdev forbids using CI as a build service. Authors must verify locally before posting. This is a burden statement about compile-checking.
    quote: "Do not post your patches just to run them through the checks." ... "You must ensure that your patches are ready by testing them locally before posting to the mailing list."
    source: Networking subsystem (netdev) |  | docs.kernel.org | https://docs.kernel.org/process/maintainer-netdev.html
    candidate_problem: A local, fast, pre-posting check of 'is the touched object covered by the configs I built' would reduce wasted CI and reviewer cycles.

[236] (policy/policy, n.d.) KVM x86 requires every patch in a series to build for a fixed config. It concedes that exhaustive config coverage is infeasible and names the Kconfig knobs to vary.
    quote: "At a bare minimum, all patches in a series must build cleanly for KVM_INTEL=m KVM_AMD=m, and KVM_WERROR=y." ... "Building every possible combination of Kconfigs isn't feasible, but the more the merrier."
    source: KVM x86 maintainer profile |  | docs.kernel.org | https://docs.kernel.org/process/maintainer-kvm-x86.html
    candidate_problem: Maintainers say outright that full config coverage is infeasible. A per-object condition gives a targeted minimal set instead of 'the more the merrier'.

[239] (policy/policy, n.d.) Media patches advance only if they pass the Media CI, which makes CI build coverage the gate.

[246] (policy/policy, n.d.) NFSD profile describes a soak period in which patches are exposed to zero-day bots and static analyzers. Compile-level breakage is caught after merge by community bots as much as by the author.
